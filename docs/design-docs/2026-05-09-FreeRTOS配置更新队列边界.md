# FreeRTOS 配置更新队列边界

## 背景

`communication_task` 已经能通过 `command_responder` 处理 `SET` 命令，`environment_processor` 也已经提供 `environment_processor_update_config` 作为安全更新入口。

缺口在于：两个 task 各自持有配置，通信任务里的配置变化还没有同步给环境处理任务。

## 决策

新增 `RTOS_QUEUE_CONFIG_UPDATE`，队列元素为完整的 `alarm_config_t`。

数据流固定为：

```text
communication_task
  -> config_update_queue
  -> env_process_task
```

## 边界

- 队列只传配置快照，不传裸指针。
- 当前只有通信任务发布配置更新，环境处理任务消费配置更新。
- `command_responder` 通过 `command_responder_status_t` 暴露 `config_changed`，不让 FreeRTOS task 重新猜测命令类型。
- 环境处理任务用 `environment_processor_update_config` 应用配置，仍然保留合法性防线。
- 队列满时当前按 best-effort 处理：通信响应仍会发出，后续可以增加错误统计或状态回读。

## 不是本次范围

- 不引入全局共享配置锁。
- 不新增配置服务任务。
- 不改变串口文本协议。
- 不做真实板上调度器运行验证。

## 后续观察点

- 如果配置更新频繁且丢失不可接受，需要把 best-effort 发送升级为阻塞发送、覆盖式 mailbox 或配置版本号。
- 如果后续有多个配置来源，需要增加配置仲裁层，而不是让多个 task 同时写环境处理器。
