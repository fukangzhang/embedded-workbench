# 环境处理步骤边界

## 背景

FreeRTOS `env_process_task` 已经能从 `sensor_sample_queue` 收到样本，调用 `alarm_state_update` 后把状态事件发给 `alarm_event_queue`。

但如果状态更新、配置持有和事件发送都写在任务函数里，后续做主机测试、配置更新和真实传感器接入时，任务代码会越来越重。

## 决策

新增 app 层 `environment_processor_t`：

```c
typedef bool (*environment_processor_publish_fn)(void *context, alarm_state_t state);

typedef struct {
    alarm_config_t config;
    alarm_state_t state;
    environment_processor_publish_fn publish;
    void *publish_context;
} environment_processor_t;
```

核心流程是：

```text
sensor_sample_t
  -> alarm_state_update
  -> publish(alarm_state_t)
```

另外提供 `environment_processor_update_config`，用于把新的合法 `alarm_config_t` 快照复制进 processor。它只负责安全更新配置，不负责配置从哪个任务传来。

## 分层位置

这个模块放在 `app/`，因为它组织的是应用业务流程：

- `alarm_state` 只负责状态机算法。
- `environment_processor` 持有配置和当前状态，并决定何时发布状态事件。
- FreeRTOS task 只负责阻塞等 queue 和周期调度。

## 当前接入

FreeRTOS `env_process_task` 现在初始化一个 `environment_processor_t`，收到样本后调用 `environment_processor_process_sample`。

发布回调 `freertos_publish_alarm_event` 负责把状态包装成内部 `freertos_alarm_event_t` 并送入 `alarm_event_queue`。

当前 `environment_processor_update_config` 还没有接到 FreeRTOS 任务间消息通道；它是后续配置同步的落点。

## 不做什么

- 不直接驱动 LED、蜂鸣器或执行器。
- 不读取真实传感器。
- 不解析串口命令。
- 不处理运行时 SET 阈值命令从通信任务传到环境任务的消息通道。

运行时配置同步会牵涉通信任务和环境任务之间的共享/消息机制，应单独设计。
