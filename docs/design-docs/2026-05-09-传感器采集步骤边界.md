# 传感器采集步骤边界

## 背景

项目已经有两层能力：

- `sensor_source_t`：定义“从哪里读一帧 sample”。
- `rtos_port` / FreeRTOS queue：定义“sample 后续要进入任务间数据流”。

如果每个任务都自己写 `sensor_source_read -> xQueueSend`，后续真实传感器、仿真 source 和错误处理会散落在任务代码里。

## 决策

新增 app 层 `sensor_acquisition_t`：

```c
typedef bool (*sensor_acquisition_submit_fn)(void *context, const sensor_sample_t *sample);

typedef struct {
    const sensor_source_t *source;
    sensor_acquisition_submit_fn submit;
    void *submit_context;
} sensor_acquisition_t;
```

`sensor_acquisition_poll` 只做一件事：

```text
sensor_source_read(source)
  -> submit(sample)
```

它不关心 sample 来自序列、I2C、ADC 还是测试 fake，也不关心 submit 最后落到 FreeRTOS queue、主机 fake 还是别的管道。

## 分层位置

这个模块放在 `app/`，不是 `drivers/`：

- `drivers/` 负责提供 sample、source、串口、GPIO 等可复用底层能力。
- `app/` 负责把这些能力组织成业务流程。

采集步骤正好是“读取来源”和“送入后续应用数据流”的流程边界，所以属于 app 层。

## 当前接入

FreeRTOS `sensor_acquire_task` 现在创建一个 `sensor_acquisition_t`，每个周期调用 `sensor_acquisition_poll`。

提交回调 `freertos_submit_sensor_sample` 负责把 sample 送进 `sensor_sample_queue`。

## 不做什么

- 不直接访问真实传感器寄存器。
- 不直接判断告警状态。
- 不格式化串口响应。
- 不启动 FreeRTOS 调度器。

这些职责已经分别属于 source 实现、`alarm_state`、命令/响应模块和固件入口。
