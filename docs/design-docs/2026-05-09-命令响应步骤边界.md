# 命令响应步骤边界

## 背景

FreeRTOS `communication_task` 已经有 `command_queue` 和 `response_queue`，但之前收到命令后只返回固定 `OK`，只能证明队列通路存在，不能证明命令处理逻辑已经接入 RTOS 通信任务。

项目已经有两块成熟能力：

- `command_handler`：处理已经解析好的 `command_t`，修改配置或样本。
- `response_format`：把结果、状态和配置格式化成串口可读文本。

## 决策

新增 app 层 `command_responder_t`：

```c
typedef struct {
    alarm_config_t *config;
    alarm_state_t *state;
    sensor_sample_t *sample;
} command_responder_t;
```

它的核心流程是：

```text
command_t
  -> command_handler_handle
  -> response_format_result
  -> optional response_format_config/status
```

## 分层位置

`command_responder` 放在 `app/`：

- parser 仍然属于 `drivers/`，只负责文本到 `command_t`。
- handler 负责业务修改和请求标志。
- responder 负责把 handler 结果组织成完整响应文本。
- FreeRTOS task 负责从 queue 收命令、把响应送回 queue。

## 当前接入

FreeRTOS `communication_task` 现在初始化一个 `command_responder_t`，收到 `command_t` 后调用 `command_responder_handle_command`，成功后把响应写入 `response_queue`。

`rtos_response_message_t` 的文本空间显式定义为 512 字节，并且 `rtos_task_model` 使用 `sizeof(rtos_response_message_t)` 作为 `response_queue` 元素大小，避免队列复制尺寸和真实消息结构体不一致。

## 不做什么

- 不改变文本命令 parser。
- 不改变串口逐字节读取链路。
- 不解决通信任务和环境处理任务之间的配置同步。
- 不证明真实板上 FreeRTOS 调度器已经运行。

运行时配置同步会影响多个任务的状态一致性，需要后续单独设计。
