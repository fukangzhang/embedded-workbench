# 固件告警输出链路自检

## 这一阶段在做什么？
前面几步已经把告警输出链路搭出来：

```text
alarm_output
  -> alarm_output_digital_sink
  -> digital_output
  -> board_digital_output
```

这一阶段把这条链路接进 `firmware/src/main.c` 的自检里。这样固件 ELF 构建时，不只是编译这些模块，还会在入口代码中实际引用并连接它们。

## 对应代码
- `firmware/src/main.c`
- `app/include/embedded_workbench/alarm_output_digital_sink.h`
- `drivers/include/embedded_workbench/board_digital_output.h`
- `bsp/include/embedded_workbench/board_profile.h`

## 自检检查什么？
`firmware_alarm_output_self_check` 做了这些事：

1. 取默认 `board_profile`
2. 初始化 `board_digital_output`
3. 初始化 `alarm_output_digital_sink`
4. 生成 `ALARM_STATE_ALARM` 对应的输出命令
5. 应用输出命令
6. 检查 LED、蜂鸣器、执行器都被记录为 `high`

这说明从告警状态到板级输出后端的链接已经通了。

## 这还不是板上运行验证
当前自检只发生在代码路径和链接层面。它能证明：

- 头文件和库依赖能正确组合
- 固件入口能引用完整输出链路
- profile-backed 后端能记录预期状态

它不能证明：

- 真实 GPIO 已经初始化
- 板上 PA5/PB6/PB7 已经变电平
- 蜂鸣器或执行器已经真的动作

这些要等后续 STM32 GPIO 后端和板上 bring-up。

## 面试里怎么讲？
可以这样说：

> 我把告警输出链路纳入了固件入口自检。虽然当前还没有真实 GPIO 写入，但固件 ELF 已经覆盖了从告警状态、输出策略、sink 适配器、数字输出到 board profile 后端的完整链接。这能降低后续接硬件时的集成风险。
