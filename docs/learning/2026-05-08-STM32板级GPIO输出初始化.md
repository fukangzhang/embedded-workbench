# STM32 板级 GPIO 输出初始化

## 这一阶段在做什么？
前面已经分别做了三块低层能力：

```text
stm32_rcc_gpio_clock -> 打开 GPIO 端口时钟
stm32_gpio_config    -> 配置 GPIO 输出模式
stm32_gpio_output    -> 写 BSRR 输出高/低电平
```

这一阶段新增 `stm32_board_gpio_init`，把前两步按板级 profile 串起来：对告警 LED、蜂鸣器、执行器三个输出引脚，先打开端口时钟，再配置为输出模式。

## 对应代码
- `drivers/include/embedded_workbench/stm32_board_gpio_init.h`
- `drivers/src/stm32_board_gpio_init.c`
- `tests/test_stm32_board_gpio_init.c`
- `CMakeLists.txt`

## 为什么需要这一层？
单独的 RCC/GPIO 模块只知道“怎么操作寄存器”，不知道项目里哪些引脚需要初始化。`board_profile` 知道项目使用了：

- `alarm_led`
- `alarm_buzzer`
- `alarm_actuator`

`stm32_board_gpio_init` 就是把“板子上有哪些输出引脚”和“STM32 GPIO 初始化步骤”接起来。

## 初始化顺序
每个 pin 都按这个顺序处理：

```text
stm32_rcc_enable_gpio_port_clock
  -> stm32_gpio_configure_output
```

这个顺序不能反过来。真实 STM32 上，如果没有先打开 GPIO 端口时钟，后续配置 GPIO 寄存器就没有可靠基础。

## 代码怎么读？
建议按这个顺序：

1. `stm32_board_gpio_init.h`
   - 看公开函数 `stm32_board_gpio_init_alarm_outputs`
2. `stm32_board_gpio_init.c`
   - 先看 `init_output_pin`
   - 再看三个 profile 引脚如何被依次初始化
3. `tests/test_stm32_board_gpio_init.c`
   - 看测试如何用普通变量模拟 RCC 和 GPIO 寄存器
   - 看成功路径如何验证 PA5、PB6、PB7 都被配置
   - 看失败路径如何验证中途失败后不会继续配置后续 pin

## 为什么还不写初始电平？
这一步只负责“让 pin 成为可输出的 GPIO”。真正输出高低电平仍然由 `stm32_gpio_output` 负责。

这样拆开后，后续启动流程可以更清楚：

```text
board init
  -> 初始化 GPIO 输出能力

alarm output
  -> 根据告警状态写高/低电平
```

初始化阶段不应该顺手塞入告警业务逻辑。

## 这一步还不能证明什么？
这一步仍然不能证明真实板上 LED/蜂鸣器/执行器动作。它只证明：

- profile 中的三个告警输出 pin 会按顺序初始化
- RCC 时钟和 GPIO 配置模块能被正确组合
- 默认输出配置能生效
- 中途失败时会返回失败并停止后续初始化

真实板上还需要真实 RCC/GPIO 地址绑定、启动入口调用和板上验证。

## 面试里怎么讲？
可以这样说：

> 我把 STM32 GPIO 输出初始化拆成了可测试的组合层：底层模块分别处理 RCC 时钟和 GPIO 配置，板级初始化层根据 board_profile 找到项目需要的告警输出引脚并按顺序初始化。这样既保留了硬件接入的真实流程，又能在没有开发板时用主机测试验证初始化顺序和失败处理。
