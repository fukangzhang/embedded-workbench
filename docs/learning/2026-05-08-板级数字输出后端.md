# 板级数字输出后端

## 这一阶段在做什么？
前面已经有了通用数字输出接口：

```text
digital_output_write(controller, pin, level)
```

这一阶段新增一个基于 `board_profile_t` 的后端：

```text
board_digital_output
  -> 识别 alarm_led / alarm_buzzer / alarm_actuator
  -> 记录每个输出脚当前是 high 还是 low
```

它还不是真实 STM32 GPIO，但已经是一个真正的 `digital_output_ops_t.write` 实现。

## 对应代码
- `drivers/include/embedded_workbench/board_digital_output.h`
- `drivers/src/board_digital_output.c`
- `tests/test_board_digital_output.c`
- `drivers/include/embedded_workbench/digital_output.h`
- `bsp/include/embedded_workbench/board_profile.h`

## 为什么需要这一层？
`digital_output` 是接口，只有接口还不能保存或执行输出结果。

`board_digital_output` 做的是第一版后端：

- 用 `board_profile_t` 确认哪些引脚属于本项目告警输出
- 接收 `digital_output_write` 的写入请求
- 记录 LED、蜂鸣器、执行器的当前电平
- 拒绝 profile 之外的未知引脚

这让我们可以在没有真实开发板时验证“写 GPIO”这一层的行为。

## 和真实 GPIO 的区别
当前后端只是记录状态：

```text
alarm_led_level = high/low
alarm_buzzer_level = high/low
alarm_actuator_level = high/low
```

真实 STM32 GPIO 后端后续会把同样的写入动作替换成：

```text
HAL_GPIO_WritePin(...)
```

或寄存器级写法。

也就是说，应用层和测试不用关心后端到底是“记录状态”还是“真实写引脚”。

## 当前完整链路
现在告警输出链路可以理解成：

```text
alarm_state
  -> alarm_output
  -> alarm_output_sink
  -> alarm_output_digital_sink
  -> digital_output
  -> board_digital_output
  -> board_profile
```

下一步可以选择：

- 把 FreeRTOS context 默认接上 `board_digital_output`
- 或新增真正的 STM32 GPIO/HAL 后端
- 或补输出节拍，让 indicator 按 `period_ms` 闪烁

## 面试里怎么讲？
可以这样说：

> 我先实现了一个基于 board profile 的数字输出后端，用于记录和验证 LED、蜂鸣器、执行器的输出电平。它遵守和真实 GPIO 后端相同的 digital_output 接口，所以后续替换成 STM32 HAL 时，不需要改告警状态机和输出策略。
