# 命令解析

## 这一阶段在做什么？
项目后续会通过串口或主机仿真输入命令，例如：

```text
STATUS?
CONFIG?
CLEAR_ALARM
SET TEMP_WARN 350
SAMPLE 360 600 250 20
```

这一阶段只做一件事：把文本命令解析成结构体。

## 为什么不直接在解析时改配置？
解析器的职责应该很小：判断一段文本是不是合法命令，并把它转换成结构化数据。

它不应该直接修改告警配置，也不应该直接控制硬件。原因是：

- 更容易测试
- 更容易复用
- 错误输入不会直接影响系统状态
- 后续串口、USB 或主机输入都可以共用解析器

所以当前解析结果是：

```c
typedef struct {
    command_type_t type;
    command_threshold_t threshold;
    int32_t value;
    int32_t sample_temperature_c_x10;
    int32_t sample_humidity_rh_x10;
    int32_t sample_light_lux;
    int32_t sample_smoke_ppm;
} command_t;
```

真正执行命令，会放到后续命令处理模块中。

## 当前支持的命令

`STATUS?`

查询当前系统状态。后续会返回传感器数据和告警状态。

`CONFIG?`

查询当前阈值配置。

`CLEAR_ALARM`

清除或确认告警。第一版只解析，不执行。

`SET <字段> <数值>`

设置阈值，例如：

```text
SET TEMP_WARN 350
SET SMOKE_ALARM 500
SET LIGHT_ALARM_LOW 30
```

`SAMPLE <温度x10> <湿度x10> <光照lux> <烟雾ppm>`

注入一帧传感器样本，用于没有真实传感器时的调试和演示，例如：

```text
SAMPLE 360 600 250 20
```

## 为什么命令先用大写？
第一版命令解析先采用严格大写，减少解析器复杂度。等协议稳定后，可以再决定是否支持大小写不敏感、缩写或更复杂的帧格式。

## 这和串口有什么关系？
真实串口收到的是一串字节。通常做法是：

1. UART 中断或 DMA 收到字节
2. 通信任务把字节拼成一行命令
3. 调用 `command_parse`
4. 得到结构化命令
5. 命令处理模块执行对应动作

当前只做第 3 步，后续再补第 4、5 步。
