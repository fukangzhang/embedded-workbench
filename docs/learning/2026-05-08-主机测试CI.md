# 主机测试 CI

## CI 是什么？
CI 是持续集成。对这个项目来说，它最直接的作用是：每次提交或开 PR 时，自动在 GitHub 服务器上重新编译并运行测试。

这样可以避免一种常见问题：本地能跑，但别人拉下来或换台机器就坏了。

## 这一阶段 CI 做了什么？
当前 workflow 位于：

```text
.github/workflows/ci.yml
```

它会执行：

```bash
cmake -S . -B build -G Ninja
cmake --build build
ctest --test-dir build --output-on-failure
```

也就是把我们本地一直手动跑的验证搬到 GitHub Actions。

## 为什么先只跑主机测试？
当前项目还没有真实 STM32 工程、启动文件、链接脚本和交叉工具链配置。

但是核心逻辑已经可以在主机上验证：

- 传感器数据模型
- 告警状态机
- 命令解析
- 命令处理
- 响应格式
- FreeRTOS 任务模型描述

所以第一版 CI 先覆盖这些内容。等目标板工程接入后，再加交叉编译 job。

## 为什么用 Ubuntu？
Linux CI 环境启动快、工具链容易安装，而且我们的代码是标准 C，不依赖 Windows 专属 API。

当前 workflow 使用：

- `ubuntu-latest`
- 系统 CMake
- `ninja-build`
- 默认 C 编译器

这能证明项目不是只在本机临时工具链下能跑。

## 后续可以增强什么？
后续可以逐步加入：

- Windows CI
- 代码格式检查
- 静态分析
- 覆盖率报告
- STM32 交叉编译
- 固件产物上传

但当前阶段先保证最核心的一件事：每个 PR 都能自动编译并跑测试。
