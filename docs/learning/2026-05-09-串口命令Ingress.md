# 串口命令 Ingress

## 这一步做了什么？

新增一个 app 层模块：

```text
serial_command_ingress
```

它负责把串口逐字节输入变成 `command_t`：

```text
byte stream
  -> serial_line
  -> command_parse
  -> submit(command_t)
```

这里的 `ingress` 可以理解成“入口”。它只把外部输入整理成内部命令对象，不直接修改配置，也不直接生成响应。

## 对应代码

- `app/include/embedded_workbench/serial_command_ingress.h`
- `app/src/serial_command_ingress.c`
- `tests/test_serial_command_ingress.c`
- `CMakeLists.txt`

## 它和 serial_command_service 有什么区别？

`serial_command_service` 是完整裸机服务：

```text
byte
  -> line
  -> command_session
  -> response text
  -> writer
```

它适合没有 RTOS 的轮询 loop，因为收到一整行后可以立刻处理并写回串口。

`serial_command_ingress` 则只做到：

```text
byte
  -> line
  -> command_t
  -> submit callback
```

这更适合 FreeRTOS。后续 submit callback 可以把 `command_t` 发送到 `command_queue`，再由 `communication_task` 统一处理响应。

## 为什么无效命令也会 submit？

当输入是：

```text
NOT_A_COMMAND
```

`command_parse` 会失败。`serial_command_ingress` 不直接回错误文本，而是提交一个 `COMMAND_TYPE_INVALID`。

这样后续 `command_responder` 可以统一生成：

```text
ERR result=invalid-command
```

也就是说，错误响应策略仍然集中在响应层，而不是散落到串口入口层。

## 状态枚举怎么理解？

```c
SERIAL_COMMAND_INGRESS_STATUS_IDLE
```

表示还没收完整一行。

```c
SERIAL_COMMAND_INGRESS_STATUS_COMMAND_SUBMITTED
```

表示已经解析并提交了一条 `command_t`。

```c
SERIAL_COMMAND_INGRESS_STATUS_OVERFLOW
```

表示当前行超过了接收缓冲区。模块会复位行缓冲，下一行仍然可以继续处理。

```c
SERIAL_COMMAND_INGRESS_STATUS_ERROR
```

表示参数无效或 submit 回调失败。

## 测试覆盖了什么？

`tests/test_serial_command_ingress.c` 覆盖：

- 没有换行时保持 idle，不提交命令。
- `STATUS?` 换行后提交 `COMMAND_TYPE_GET_STATUS`。
- `SET TEMP_WARN 360` 的字段解析后完整提交。
- 无效命令会提交 `COMMAND_TYPE_INVALID`。
- `CRLF` 只提交一次。
- 行溢出后能恢复处理下一行。
- submit 回调失败会返回 error。
- 初始化和 feed 的空指针防御路径。

## 看完要能解释什么？

- 为什么 FreeRTOS 串口输入不直接用 `serial_command_service`
- 为什么入口层只提交 `command_t`，不处理业务状态
- 为什么无效命令也要走 `command_t` 和 responder
- `serial_line`、`command_parser`、`serial_command_ingress` 三者怎么分工
