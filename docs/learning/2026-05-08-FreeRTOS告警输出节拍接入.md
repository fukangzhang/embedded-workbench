# FreeRTOS 告警输出节拍接入

## 这一阶段在做什么？
前面已经有了两块：

```text
alarm_event_queue -> alarm_output_task
alarm_output_timing -> indicator 当前亮/灭
```

这一阶段把它们接起来。`alarm_output_task` 收到告警事件后，不只是应用一次输出命令，而是保存当前输出命令，并周期性刷新 indicator 亮灭。

## 对应代码
- `app/src/rtos_port_freertos.c`
- `app/include/embedded_workbench/alarm_output_timing.h`
- `app/src/alarm_output_timing.c`

## 当前任务逻辑
告警输出任务现在大致是：

```text
等待 alarm_event_queue
  -> 收到新状态
  -> alarm_output_command_for_state
  -> elapsed_ms = 0

之后每 50ms：
  -> alarm_output_indicator_is_on(command, elapsed_ms)
  -> 当前应该灭时，把 indicator 临时改成 off
  -> alarm_output_sink_apply
```

其中 buzzer 和 actuator 仍然来自原始输出命令，不会因为 indicator 闪烁而一起闪烁。

## 为什么先固定 50ms？
50ms 是当前构建级骨架的刷新间隔。它足够细，可以表达 250ms、500ms、1000ms 这些告警节拍；也不会把任务模型做得太复杂。

后续如果需要，可以把它移到：

- task model 配置
- build-time 配置
- 运行时配置

## 这一步还不能证明什么？
当前验证仍然是构建和链接级：

- FreeRTOS 任务代码能编译
- 调度器构建能链接
- timing 逻辑已经接进任务代码路径

它还不能证明真实板上的 LED 已经按节拍闪烁。那需要真实 GPIO 后端和板上运行验证。

## 面试里怎么讲？
可以这样说：

> 我把告警输出任务改成了事件驱动加周期刷新：事件负责更新当前告警状态，周期刷新负责按照 period_ms 计算指示灯当前亮灭。这样任务调度和节拍规则是分离的，主机侧可以测试节拍规则，FreeRTOS 侧负责按固定频率调用。
