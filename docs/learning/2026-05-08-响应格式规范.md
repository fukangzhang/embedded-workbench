# 响应格式规范

## 为什么要单独做响应格式？
前面已经能解析命令、处理命令，但输出响应如果散落在各个地方手写，很快会变乱。

例如同样表示成功，有的地方写：

```text
OK
```

有的地方写：

```text
response result=ok
```

后续上位机或测试脚本就很难稳定解析。

所以这一阶段把响应格式集中到 `response_format` 模块里。

## 为什么放在 app？
响应格式需要知道：

- 告警状态
- 告警配置
- 命令处理结果
- 传感器样本

这些信息跨越了 `drivers` 和 `app`。如果把响应格式放到 `drivers`，会让 `drivers` 反向依赖 `app`，破坏 `bsp -> drivers -> app` 的方向。

所以当前放在 `app/`，由应用层决定如何对外表达系统状态。

## 当前响应格式
命令处理结果：

```text
OK result=ok
ERR result=invalid-value
```

状态：

```text
STATUS state=warning temp_c_x10=253 humidity_rh_x10=604 light_lux=350 smoke_ppm=12
```

配置：

```text
CONFIG temp_warn=350 temp_alarm=450 ...
```

第一版采用键值对文本格式，原因是：

- 人能直接读
- 脚本容易解析
- 串口调试工具里好观察
- 比 JSON 更轻

## 为什么响应里不用小数？
协议响应里使用 `temp_c_x10=253`，而不是 `25.3C`。

这是为了保持和内部数据模型一致：

- 更容易被 MCU 和脚本处理
- 避免浮点格式差异
- 测试更稳定

展示层如果想显示 `25.3°C`，可以在上位机或 UI 里转换。

## 后续可以怎么增强？
后续接真实串口时，可以考虑：

- 增加帧头帧尾
- 增加错误码
- 增加命令序号
- 增加 CRC
- 统一换行规则
- 支持更机器友好的 JSON-like 格式

这些先不急。当前目标是让响应稳定、集中、可测试。
