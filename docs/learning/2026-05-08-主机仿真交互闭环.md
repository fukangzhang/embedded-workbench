# 主机仿真交互闭环

## 这一阶段在做什么？
前面已经有了：

- 传感器数据模型
- 告警状态机
- 命令解析器
- 命令处理器

这一阶段把它们接到 `host_sim` 里，让电脑上的程序可以演示一条完整链路：

```text
模拟传感器样本 -> 告警状态机 -> 状态输出
文本命令 -> 命令解析 -> 命令处理 -> 配置变化
```

这还不是目标板固件，但已经能展示核心业务逻辑。

## 为什么先做主机仿真？
真实硬件还没接入时，如果只能看代码，很难判断逻辑是否真的工作。

主机仿真能带来几个价值：

- 不依赖开发板也能运行
- 可以快速观察状态变化
- 可以配合自动化测试
- 可以作为后续串口协议的演示入口

这对学习和简历都很有帮助，因为你不仅能说“我写了状态机”，还能演示它怎么跑。

## 默认模式和脚本模式
默认运行：

```powershell
build\host_sim.exe
```

程序会输出项目名、运行模式和一组内置模拟样本的状态变化。

脚本模式：

```powershell
build\host_sim.exe --script
```

脚本模式会从标准输入读取命令，例如：

```text
STATUS?
CONFIG?
SET TEMP_WARN 360
CLEAR_ALARM
```

当前它适合后续用重定向、脚本或测试工具驱动。

## 这和真实串口有什么关系？
真实串口最终也会收到类似的文本命令。区别只是来源不同：

- 主机仿真：命令来自标准输入
- STM32 目标板：命令来自 UART 接收缓冲区

只要最终得到一行字符串，就可以调用同一个 `command_parse` 和 `command_handler_handle`。

这就是接口隔离带来的好处：输入来源可以变，但核心逻辑不需要重写。

## 当前还缺什么？
当前主机仿真还很朴素：

- 没有实时采样循环
- 没有漂亮界面
- 没有串口收发
- 没有 FreeRTOS 任务
- 没有保存配置

这些都可以后续逐步加，但现在已经形成了第一条可运行闭环。
