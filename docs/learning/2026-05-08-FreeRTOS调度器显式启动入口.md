# FreeRTOS 调度器显式启动入口

## 这一阶段在做什么？
前面已经完成了三件事：

- FreeRTOS-Kernel 能链接进固件
- `rtos_port` 能用 FreeRTOS queue 收发消息
- `rtos_port_start()` 能创建四个 FreeRTOS task

这一阶段新增的是调度器启动入口：

```c
freertos_rtos_port_start_scheduler(...)
```

并通过 CMake 开关控制 firmware 是否真的调用它：

```cmake
EW_FREERTOS_START_SCHEDULER
```

默认值是 `OFF`。

## 为什么调度器启动要显式开关？
`vTaskStartScheduler()` 和普通函数不一样。

普通函数调用完会返回，调用方可以继续执行后面的代码。FreeRTOS 调度器启动成功后，CPU 会进入任务调度，不再按原来的 `main()` 顺序往下走。

也就是说：

```c
vTaskStartScheduler();
```

正常情况下不会返回。只有调度器启动失败，或者某些特殊 port 支持结束调度时，后面的代码才可能继续执行。

所以当前不把它默认打开，而是让固件构建显式选择：

```powershell
-D EW_FREERTOS_START_SCHEDULER=ON
```

## 这一步验证了什么？
当前验证的是“启动路径可以编译和链接”：

- 固件能引用 `vTaskStartScheduler`
- 任务创建路径能和 scheduler handoff 连起来
- scheduler 启动前 FreeRTOS context 已经准备好默认模拟 `sensor_source` 和 `alarm_output_sink`
- CI 能构建 scheduler 开关打开的 firmware ELF

这还不等于“已经在板子上跑起来”。

## 为什么还不能声称板上运行成功？
真实运行还需要硬件侧证据：

- SysTick 是否按预期产生 tick
- SVC handler 是否进入第一个任务
- PendSV handler 是否能切换上下文
- 中断优先级配置是否符合 FreeRTOS 约束
- 任务栈大小是否足够
- Cortex-M3 port 用于当前非 FPU 初期验证是否满足板上策略

这些必须通过板上调试或仿真记录确认。

## 当前代码怎么组织？
`rtos_port_start()` 仍然负责创建任务。

在启动 scheduler 前，固件 FreeRTOS 路径会先准备运行期资源：

```text
sequence_sensor_source
  -> context.sensor_source

alarm_output_sink
  -> context.alarm_output_sink
```

这让采集任务和输出任务启动后都有明确依赖，而不是只创建空任务骨架。

新增的 `freertos_rtos_port_start_scheduler()` 负责最后一步 handoff：

```c
if (!tasks_are_created(context)) {
    return false;
}

vTaskStartScheduler();

return false;
```

最后的 `return false` 是有意的：如果调度器启动成功，正常不会运行到这里；如果运行到了这里，说明启动没有成功完成。

## 当前 CI 多验证了什么？
FreeRTOS firmware job 现在验证两种构建：

- `EW_USE_FREERTOS=ON`
- `EW_USE_FREERTOS=ON` 且 `EW_FREERTOS_START_SCHEDULER=ON`

前者验证 FreeRTOS 内核、队列和任务创建路径；后者额外验证 scheduler handoff 路径能链接。

## 后续还缺什么？
任务函数已经具备模拟输入、配置同步、环境处理、通信响应和告警输出 sink 接线。下一步重点转向真实板上启动 scheduler 并记录调试证据。
