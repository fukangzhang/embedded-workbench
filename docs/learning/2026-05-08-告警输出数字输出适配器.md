# 告警输出数字输出适配器

## 这一阶段在做什么？
前面已经有两块：

```text
alarm_output_sink
digital_output
```

这一阶段把它们接起来：

```text
alarm_output_sink
  -> alarm_output_digital_sink
  -> digital_output_write
  -> board_profile 里的告警输出引脚
```

这样告警输出命令不再只是抽象动作，而是能映射到板级 profile 里的三类输出：

- `alarm_led`
- `alarm_buzzer`
- `alarm_actuator`

## 对应代码
- `app/include/embedded_workbench/alarm_output_digital_sink.h`
- `app/src/alarm_output_digital_sink.c`
- `tests/test_alarm_output_digital_sink.c`
- `drivers/include/embedded_workbench/digital_output.h`
- `bsp/include/embedded_workbench/board_profile.h`

## 适配器做了什么？
`alarm_output_digital_sink_init` 会把一个 `alarm_output_sink_t` 初始化成数字输出版本。

之后调用：

```text
alarm_output_sink_apply
```

会依次触发：

```text
set_indicator -> digital_output_write(profile->alarm_led, high/low)
set_buzzer    -> digital_output_write(profile->alarm_buzzer, high/low)
set_actuator  -> digital_output_write(profile->alarm_actuator, high/low)
```

当前 `indicator` 只转换成开/关：只要不是 `off` 就写高电平。`period_ms` 先保留，后续由任务节拍或定时器处理闪烁。

## 为什么放在 app？
这个适配器同时认识两边：

- 上层：`alarm_output_sink`
- 下层：`digital_output`

它的职责是“把告警语义翻译成驱动调用”，所以放在 `app` 比放在 `drivers` 更合适。`drivers` 不应该知道告警状态机，也不应该知道什么是 buzzer 或 actuator。

## 现在仍然没有真实 GPIO
测试里还是 fake `digital_output`。它只记录：

- 写了第几个引脚
- 写成高电平还是低电平
- 底层失败时是否停止后续输出

真实 STM32 GPIO 写入会在后续任务中接到 `digital_output` 的 `write` 回调。

## 面试里怎么讲？
可以这样说：

> 我用适配器把应用层的告警输出 sink 和底层数字输出驱动连接起来。告警模块只输出语义化命令，适配器负责查 board profile 并调用数字输出接口。这样状态机、驱动和目标板引脚映射各自独立，便于测试和替换。
