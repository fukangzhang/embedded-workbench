# FreeRTOS 告警事件流骨架

## 这一阶段在做什么？
任务模型里早就定义了四条队列：

- `sensor_sample_queue`
- `command_queue`
- `response_queue`
- `alarm_event_queue`

上一阶段 FreeRTOS port 已经接入了前三条队列。这一阶段把第四条 `alarm_event_queue` 接上。

## alarm_event_queue 有什么用？
环境处理任务负责判断传感器样本是否触发告警，但它不应该直接控制 LED、蜂鸣器或执行器。

更好的方式是：

- `env_process_task` 读取传感器样本
- 调用 `alarm_state_update`
- 把新的告警状态封装成事件
- 发送到 `alarm_event_queue`
- `alarm_output_task` 从队列里取事件
- 后续再决定如何驱动硬件输出

这样处理逻辑和输出逻辑是分开的，后面换 LED、蜂鸣器或继电器时，不需要改环境处理任务。

## 为什么不改公共 rtos_port 接口？
`rtos_port` 是应用层和 RTOS 实现之间的公共边界。它现在只暴露启动、发送传感器样本、发送命令、接收响应这些外部需要的动作。

告警事件流属于 FreeRTOS 任务内部协作。当前把它放在 `rtos_port_freertos` 内部，不把细节暴露给 host fake port，可以保持公共接口小而稳定。

## 当前实现了什么？
`freertos_rtos_port_context_t` 新增：

```c
QueueHandle_t alarm_event_queue;
```

`freertos_rtos_port_init()` 会创建：

```c
RTOS_QUEUE_ALARM_EVENT
```

`env_process_task` 在更新状态后发送事件：

```c
event.state = state;
xQueueSend(context->alarm_event_queue, &event, 0);
```

`alarm_output_task` 阻塞等待事件：

```c
xQueueReceive(context->alarm_event_queue, &event, portMAX_DELAY);
```

## 当前还不做什么？
告警输出任务现在只是消费事件，还没有驱动实际硬件。

这是有意的：先把任务之间的数据通道打通，再接 LED、蜂鸣器或执行器，问题会更容易定位。

## 当前验证说明
本阶段验证：

- host 测试仍然通过
- 普通 firmware ELF 能构建
- FreeRTOS firmware ELF 能构建
- scheduler 开关打开的 firmware ELF 能构建

这说明告警事件流已经参与 FreeRTOS 固件编译和链接，但还没有声称真实硬件输出已经完成。

## 后续还缺什么？
下一步可以做告警输出适配：

- 定义告警输出驱动接口
- host 侧 fake 输出用于测试
- firmware 侧先接一个简单 BSP stub
- 后续映射到 LED、蜂鸣器或继电器
