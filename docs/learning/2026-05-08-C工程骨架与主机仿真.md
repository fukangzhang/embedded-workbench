# C 工程骨架与主机仿真

## 这一阶段在做什么？
这一阶段不是实现业务功能，而是先建立一个可以继续长大的 `C` 工程：

- 有核心库：以后放可复用业务逻辑
- 有主机仿真程序：不用开发板也能运行
- 有测试程序：每加一个核心逻辑都能验证
- 有 CMake：统一描述如何编译和测试

## 为什么要先做核心库？
嵌入式项目里，最容易失控的写法是把所有逻辑都堆进 `main.c` 或某个任务函数里。这样代码一旦接入硬件，就很难在电脑上测试。

所以我们先创建 `embedded_app` 这个库。后续告警状态机、传感器数据处理、命令解析，都应该优先放进库里。

这样有两个好处：

- 主机测试可以直接链接这个库
- 目标板工程也可以链接同一套核心逻辑

## 当前文件怎么理解？

`app/include/embedded_workbench/app_info.h`

这是对外头文件。其他模块如果想知道项目名、版本、运行模式，只需要包含它。

`app/src/app_info.c`

这是实现文件。它目前很简单，只返回项目名、版本和运行模式名称。

`tools/host_sim/main.c`

这是主机仿真入口。它不是目标板固件的 `main`，而是在电脑上运行的小程序。后续它可以模拟传感器输入、打印告警状态、接收配置命令。

`tests/test_app_info.c`

这是测试入口。它用最朴素的 `return 1/2/3` 表示失败原因，避免早期就引入复杂测试框架。

## CMake 里的目标是什么意思？

`add_library(embedded_app ...)`

创建核心库。库本身不是一个可直接运行的程序，而是可复用代码集合。

`add_executable(host_sim ...)`

创建主机仿真程序。它链接 `embedded_app`，所以能调用核心库代码。

`add_executable(test_app_info ...)`

创建测试程序。它也链接 `embedded_app`，用于验证核心库行为。

`add_test(NAME app_info COMMAND test_app_info)`

把测试程序注册给 `CTest`。后续运行：

```powershell
ctest --test-dir build --output-on-failure
```

就能执行这个测试。

## 为什么现在不引入测试框架？
初期先用纯 `C` 测试程序，原因是：

- 依赖少
- 容易理解
- 更适合先把工程链路跑通

等测试数量变多后，可以再考虑 `Unity`、`Ceedling` 或其他 C 测试框架。

## 和真实 STM32 有什么关系？
现在的主机程序不是最终固件，但它验证的是将来固件也会用到的核心逻辑。

后续迁移到 STM32 时，大致会变成：

- `app/`：尽量复用
- `drivers/`：替换成真实外设实现
- `bsp/`：加入时钟、引脚、串口、I2C 等板级初始化
- `tools/host_sim/`：继续作为电脑上的演示和调试工具
- `tests/`：继续保护核心逻辑不被改坏
