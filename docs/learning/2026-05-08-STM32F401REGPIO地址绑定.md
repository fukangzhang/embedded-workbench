# STM32F401RE GPIO 地址绑定

## 这一阶段在做什么？
前面已经有了可以组合的 GPIO 初始化链路：

```text
stm32_rcc_gpio_clock
  -> stm32_gpio_config
  -> stm32_board_gpio_init
```

但这些模块之前使用的是测试里传入的模拟寄存器变量。这一阶段新增 `stm32f401re_gpio_bindings`，把 STM32F401RE 上常用的 RCC/GPIO 地址整理成一个薄层绑定：

- `RCC_AHB1ENR`
- `GPIOA`
- `GPIOB`
- `GPIOA_BSRR`
- `GPIOB_BSRR`

## 对应代码
- `drivers/include/embedded_workbench/stm32f401re_gpio_bindings.h`
- `drivers/src/stm32f401re_gpio_bindings.c`
- `tests/test_stm32f401re_gpio_bindings.c`
- `CMakeLists.txt`

## 地址绑定是什么？
可以把地址绑定理解成“把我们自己的抽象接到具体芯片地址上”。

前面的模块只需要这些信息：

```text
"PA" -> RCC enable bit 0
"PB" -> RCC enable bit 1
"PA" -> GPIOA register block
"PB" -> GPIOB register block
"PA" -> GPIOA_BSRR
"PB" -> GPIOB_BSRR
```

`stm32f401re_gpio_bindings` 就集中提供这些绑定。

## 为什么单独做一层？
如果把地址直接写进 `firmware/src/main.c` 或业务逻辑里，后面换芯片、换板子会很难改。

单独做绑定层后：

- 通用 STM32 GPIO 模块仍然只关心寄存器块和 bit
- F401RE 相关地址集中在一个地方
- 主机测试可以只验证地址常量和绑定关系
- 后续固件入口可以选择使用模拟寄存器或真实地址绑定

## 这一步还不能证明什么？
这一步还没有在固件里解引用真实地址，也没有板上运行。

它只证明：

- 地址常量能编译进工程
- PA/PB 的 RCC bit 绑定正确
- GPIOA/GPIOB 配置寄存器块地址正确地传给配置模块
- GPIOA/GPIOB 的 BSRR 地址正确地传给输出模块

真正的硬件验证还需要下载到 STM32F401RE 板子上观察 GPIO 行为。

## 代码怎么读？
建议按这个顺序：

1. `stm32f401re_gpio_bindings.h`
   - 看 `STM32F401RE_RCC_AHB1ENR_ADDRESS`
   - 看 `STM32F401RE_GPIOA_BASE_ADDRESS`
   - 看 `STM32F401RE_GPIO_BSRR_OFFSET`
2. `stm32f401re_gpio_bindings.c`
   - 看 clock/config/output 三组绑定表
3. `tests/test_stm32f401re_gpio_bindings.c`
   - 看测试如何把返回指针转回整数地址进行比较

## 面试里怎么讲？
可以这样说：

> 我没有把 STM32F401RE 的寄存器地址散落在业务代码里，而是单独做了 GPIO/RCC 地址绑定层。通用 GPIO 初始化和输出模块只依赖绑定表，后续换芯片时可以替换绑定层。当前主机测试验证地址和端口映射关系，板上运行验证会作为下一阶段。
