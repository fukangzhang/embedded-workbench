# 告警状态机

## 状态机是什么？
状态机就是把系统当前处于什么状态、遇到什么输入后切换到什么状态，明确写成代码。

本项目第一版状态包括：

- `NORMAL`：环境正常
- `WARNING`：已经接近风险，需要提醒
- `ALARM`：已经超过告警阈值，需要采取动作
- `SENSOR_FAULT`：传感器样本无效，不能相信当前数据

这样写的好处是：状态不会散落在一堆 `if` 里，后续测试和讲解都更清楚。

## 为什么状态机放在 app？
`drivers/` 负责提供传感器样本，回答“外部数据是什么”。

`app/` 负责业务规则，回答“这些数据对系统意味着什么”。

告警状态机判断的是业务含义，所以放在 `app/`。

## 什么是恢复阈值？
如果告警阈值是 `45.0°C`，温度从 `45.1°C` 降到 `44.9°C` 时，系统是否应该立刻恢复正常？

通常不应该。因为传感器数据可能抖动，如果立刻恢复，状态会在告警和正常之间来回跳。

所以我们设置恢复阈值，例如：

- 预警阈值：`35.0°C`
- 告警阈值：`45.0°C`
- 恢复阈值：`33.0°C`

进入告警后，必须降到 `33.0°C` 或更低，才认为真正恢复。这种设计叫滞回。

## 当前状态机规则
第一版规则故意保持简单：

1. 配置无效或样本无效，进入 `SENSOR_FAULT`
2. 任一指标达到告警阈值，进入 `ALARM`
3. 如果原来是 `ALARM`，但样本还没有恢复到恢复阈值以内，保持 `ALARM`
4. 任一指标达到预警阈值，进入 `WARNING`
5. 如果原来是 `WARNING`，但样本还没有恢复到恢复阈值以内，保持 `WARNING`
6. 其他情况进入 `NORMAL`

## 为什么先不做复杂策略？
真实产品里可能还会有：

- 连续多次采样确认
- 滤波
- 告警延迟
- 告警锁存
- 手动清除
- 不同传感器权重

这些都可以做，但现在先保留最小可测试状态机。项目的节奏是先把一条逻辑链路走通，再逐步增强。

## 当前测试覆盖
当前测试覆盖：

- 默认配置合法
- 正常样本输出 `NORMAL`
- 温度预警输出 `WARNING`
- 光照过低输出 `WARNING`
- 烟雾超限输出 `ALARM`
- 告警状态下未达到恢复阈值，继续保持 `ALARM`
- 告警状态下恢复正常，回到 `NORMAL`
- 无效样本进入 `SENSOR_FAULT`
- 空配置进入 `SENSOR_FAULT`
- 状态名转换
