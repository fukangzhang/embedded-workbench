# 命令会话模块

## 这一阶段在做什么？

前面已经有了几块能力：

```text
serial_line -> command_parser -> command_handler -> response_format
```

但这些模块还需要一个“胶水层”：拿到一行命令后，按固定顺序解析、执行、生成响应。

本阶段新增 `command_session`，它把一行完整命令处理成一段响应文本。以后不管命令来自主机仿真、USART2 还是 FreeRTOS 通信任务，都可以复用这层。

`host_sim` 脚本模式现在已经接入了这个模块：它仍然用 `fgets` 从标准输入读一行，但后续命令处理全部交给 `command_session_handle_line`。

## 对应代码

- `app/include/embedded_workbench/command_session.h`
- `app/src/command_session.c`
- `tests/test_command_session.c`
- `CMakeLists.txt`

## 为什么放在 app？

`command_session` 已经知道应用状态：

- 当前告警配置 `alarm_config_t`
- 当前告警状态 `alarm_state_t`
- 当前传感器样本 `sensor_sample_t`

它不只是驱动输入，也不只是字符串解析，而是在应用层把命令和当前业务状态连起来，所以放在 `app/`。

## 它负责什么？

- 调用 `command_parse` 解析完整命令行。
- 调用 `command_handler_handle` 修改配置或识别查询请求。
- 调用 `response_format_*` 生成串口/日志可输出的响应文本。
- 配置改变后，用当前样本重新计算告警状态。

## 它不负责什么？

- 不从 UART 寄存器读字节。
- 不做行缓冲。
- 不创建 FreeRTOS queue。
- 不直接操作 GPIO、蜂鸣器或执行器。

这些边界让后续通信任务更清楚：UART 负责收发字节，`serial_line` 负责拼行，`command_session` 负责业务命令响应。

## 看完以后你应该能解释什么？

- 为什么 `serial_line` 和 `command_session` 要分开。
- 为什么命令解析失败也要生成 `ERR result=invalid-command`。
- 为什么 `SET` 成功后要同时输出配置快照和状态快照。
- 为什么配置改变后要重新跑一次 `alarm_state_update`。
