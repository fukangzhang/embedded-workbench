# 环境处理步骤

## 这一步做了什么？

项目新增了一个 app 层模块：

```text
environment_processor
```

它负责把一帧传感器样本变成一个告警状态事件：

```text
sensor_sample
  -> alarm_state_update
  -> publish alarm_state
```

## 对应代码

- `app/include/embedded_workbench/environment_processor.h`
- `app/src/environment_processor.c`
- `tests/test_environment_processor.c`
- `app/src/rtos_port_freertos.c`

## 为什么要从 FreeRTOS task 里抽出来？

FreeRTOS task 应该尽量像“调度外壳”：

- 等队列消息
- 调用业务步骤
- 必要时延时或阻塞

而具体业务逻辑应该放在普通 C 模块里。这样主机测试可以不启动 FreeRTOS，也能验证：

- 样本是否正确变成 normal/warning/alarm
- 发布失败时状态是否不乱改
- 非法 sample 是否被拒绝

## environment_processor 保存了什么？

```c
typedef struct {
    alarm_config_t config;
    alarm_state_t state;
    environment_processor_publish_fn publish;
    void *publish_context;
} environment_processor_t;
```

这里把 config 和 state 放在一起，是因为状态机不是纯粹只看当前 sample。

例如已经处于 `ALARM` 时，即使 sample 回到 warning 区间，也不能立刻退出 alarm，必须达到 recovery 条件。这就是状态机里的回滞。

## publish 回调是什么？

`publish` 表示“状态算出来以后交给下一站”。

在 FreeRTOS 里，下一站是：

```text
alarm_event_queue
```

在测试里，下一站是 fake context：它只记录发布了几次、最后一次发布的状态是什么。

这种写法让环境处理模块不依赖 FreeRTOS API，也不需要知道 queue 结构。

## FreeRTOS 里怎么接上？

`env_process_task` 启动时创建：

```text
environment_processor_t processor
config = alarm_config_default()
state = ALARM_STATE_NORMAL
publish = freertos_publish_alarm_event
```

之后任务阻塞等待 `sensor_sample_queue`：

```text
xQueueReceive(sensor_sample_queue)
  -> environment_processor_process_sample
  -> xQueueSend(alarm_event_queue)
```

这样任务负责“等消息”，processor 负责“算状态并发布”。

## 配置怎么更新？

`environment_processor_update_config` 用来更新 processor 内部保存的阈值配置。

它的规则很保守：

```text
新 config 合法 -> 复制进 processor
新 config 非法 -> 返回 false，旧 config 不变
processor/config 为空 -> 返回 false
```

这样后续通信任务把 `SET` 命令产生的新配置同步过来时，环境处理器有一个安全落点：只接收完整且合法的配置快照，不接收半更新状态。

在 FreeRTOS 路径里，这个入口已经接到 `config_update_queue`：

```text
communication_task
  -> config_update_queue
  -> env_process_task
  -> environment_processor_update_config
```

环境处理任务每轮会先消费配置更新，再处理传感器样本。这样 `SET` 命令不会只停留在通信任务内部，而是会影响后续环境处理判断。

## 测试覆盖了什么？

`tests/test_environment_processor.c` 覆盖：

- normal sample 发布 normal。
- warning sample 发布 warning。
- alarm sample 发布 alarm。
- publish 失败时返回失败，而且不提交新 state。
- 非法 sample 不发布。
- 合法 config update 会影响下一次样本处理结果。
- 非法 config update 会被拒绝，而且旧 config 继续生效。
- 无效 config、无效初始 state、空指针等防御性路径。

这说明环境处理步骤可以在没有 FreeRTOS、没有硬件的情况下独立验证。

## 后面还缺什么？

当前 processor 已经可以通过 FreeRTOS 配置更新队列接收 `SET` 命令产生的新阈值。

后续还缺真实板上调度器运行验证，以及把真实传感器来源接进 `sensor_source`。
