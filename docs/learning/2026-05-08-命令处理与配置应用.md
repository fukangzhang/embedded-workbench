# 命令处理与配置应用

## 这一阶段在做什么？
上一阶段只负责把文本变成结构体，例如：

```text
SET TEMP_WARN 350
```

会被解析成：

- 类型：设置阈值
- 字段：温度预警阈值
- 值：`350`

这一阶段负责真正处理这个结构化命令，把它应用到告警配置中。

## 为什么解析和处理要分开？
解析器只回答：“这段文本是不是合法命令？”

处理器回答：“这个命令对系统状态有什么影响？”

分开以后有几个好处：

- 串口、主机 CLI、测试代码都能复用同一个处理器
- 解析错误不会直接改配置
- 配置修改可以统一校验
- 后续响应格式可以单独设计

## 当前命令处理结果
处理器返回 `command_handler_result_t`：

```c
typedef struct {
    command_result_t result;
    bool config_changed;
    bool status_requested;
    bool config_requested;
    bool sample_changed;
    bool alarm_clear_requested;
} command_handler_result_t;
```

它不是响应字符串，而是结构化结果。后续串口响应模块可以根据这些标志生成文本回复。

## 为什么设置阈值要先改副本？
如果直接修改原配置，改到一半发现配置非法，系统就可能留下一个坏状态。

当前做法是：

1. 复制一份当前配置
2. 在副本上应用新值
3. 调用 `alarm_config_is_valid`
4. 合法才写回原配置
5. 不合法就拒绝命令

这是嵌入式里很常见的防御性写法：先验证，再提交。

## 为什么要检查整数范围？
命令里的值是 `int32_t`，但配置字段可能是：

- `int16_t`
- `uint16_t`
- `uint32_t`

如果不检查就强制转换，负数或超大值可能发生回绕。例如 `70000` 转成 `uint16_t` 后会变成另一个数。

所以处理器在写入前会检查类型范围，避免错误命令变成隐藏配置问题。

## SAMPLE 为什么在 handler 里校验？

`SAMPLE` 命令会带来一帧新的传感器样本。parser 只确认它有 4 个整数，真正的范围校验放在 handler：

1. 先确认每个字段能安全落到 `sensor_sample_t` 的目标类型。
2. 再调用 `sensor_sample_is_valid` 检查物理范围。
3. 都通过才写回当前 sample。

这样错误样本不会污染当前系统状态。

## 当前测试覆盖
当前测试覆盖：

- 查询状态
- 查询配置
- 清除告警请求
- 成功设置温度预警阈值
- 成功设置烟雾告警阈值
- 拒绝破坏阈值顺序的修改
- 拒绝 unsigned 字段负数
- 拒绝 `uint16_t` 超范围值
- 拒绝光照负数
- 成功注入传感器 sample
- 拒绝越界 sample，且不修改旧 sample
- 拒绝无效命令
- 拒绝空指针输入
- 结果名转换
