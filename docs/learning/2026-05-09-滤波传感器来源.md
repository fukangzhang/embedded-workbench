# 滤波传感器来源

## 这一步做了什么？

新增模块：

```text
drivers/include/embedded_workbench/filtered_sensor_source.h
drivers/src/filtered_sensor_source.c
tests/test_filtered_sensor_source.c
```

它把两个已有概念接起来：

```text
sensor_source -> sensor_sample_filter -> sensor_source
```

也就是说，上层仍然看到一个普通 `sensor_source_t`，但每次读取时，内部会先从原始 source 读一帧 sample，再用滤波器输出更平滑的 sample。

## 为什么不直接改 sensor_acquisition？

`sensor_acquisition` 的职责是“从 source 读取，然后提交给后续队列或处理函数”。如果把滤波直接写进去，后续每个采集路径都会默认被滤波，测试和行为变化会比较大。

这一步选择做一个 wrapper：

```text
原始 source
  -> filtered_sensor_source
  -> sensor_acquisition / FreeRTOS / host test
```

这样好处是：

- 想滤波时，把原始 source 包一层。
- 不想滤波时，继续直接使用原始 source。
- 当前 `host_sim` 和 FreeRTOS 默认行为不变。

## 代码怎么对应？

头文件：

```text
drivers/include/embedded_workbench/filtered_sensor_source.h
```

里面的核心结构是：

```c
typedef struct {
    sensor_source_t inner_source;
    sensor_sample_filter_t filter;
} filtered_sensor_source_t;
```

`inner_source` 是被包装的来源。它只是复制 `read` 函数指针和 `context` 指针，不复制真实传感器状态。

源文件：

```text
drivers/src/filtered_sensor_source.c
```

读取过程是：

```text
filtered_sensor_source_read
  -> sensor_source_read(inner_source)
  -> sensor_sample_filter_apply
```

注意这里先调用 `sensor_source_read`，不是直接调用 `inner_source.read`。原因是 `sensor_source_read` 已经统一做了空指针、读取失败和 sample 合法性检查。

测试：

```text
tests/test_filtered_sensor_source.c
```

测试固定了这些行为：

- 初始化参数非法时失败。
- 第一帧 sample 直接透传。
- 第二帧 sample 按 alpha 平滑。
- reset 后下一帧重新直接透传。
- 内层 source 读取失败时，外层也返回失败。

## 和 sensor_sample_filter 的区别

`sensor_sample_filter` 只知道“给我输入 sample，我输出滤波后的 sample”。

`filtered_sensor_source` 知道“怎么从某个 source 读取 sample，并自动套滤波”。

简单说：

```text
sensor_sample_filter：算法
filtered_sensor_source：把算法挂到输入来源上的适配器
```

## 后续怎么接入？

真实传感器或 FreeRTOS 运行链路接入时，可以这样组合：

```text
real_sensor_source
  -> filtered_sensor_source
  -> sensor_acquisition
  -> sensor_sample_queue
  -> environment_processor
```

但这一步还没有默认启用它。真正启用滤波参数、决定 alpha 默认值、是否允许串口命令修改参数，都应该单独写计划处理。

## 看完要能解释什么？

- wrapper 为什么能让已有接口复用，而不是改一堆上层代码
- `inner_source` 为什么只复制接口，不复制真实上下文
- 为什么第一帧要透传
- 为什么读取失败要原样向上传递
