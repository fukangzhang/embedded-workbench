# 传感器数据模型

## 这一阶段解决什么问题？
后续项目会有温湿度、光照、烟雾等输入。真实硬件可能来自不同传感器，也可能先由主机程序模拟。

为了让上层逻辑不关心数据来自哪里，我们先定义一个统一的数据结构：

```c
typedef struct {
    int16_t temperature_c_x10;
    uint16_t humidity_rh_x10;
    uint32_t light_lux;
    uint16_t smoke_ppm;
} sensor_sample_t;
```

它的意思是“一次采集得到的一组环境数据”。

## 为什么先放在 drivers？
`drivers/` 在这个项目里不是只放真实硬件驱动，也放硬件相关接口和数据适配层。

传感器样本模型位于 `drivers/`，是因为它描述的是“外部环境数据如何进入系统”。后续可以有两种来源：

- 主机仿真：用代码生成样本
- 真实硬件：由 I2C/SPI/ADC 驱动读取后转换成样本

无论哪种来源，`app/` 都只需要处理 `sensor_sample_t`。

## 为什么不用 float？
很多 MCU 可以用 `float`，但在嵌入式项目早期，固定单位整数通常更容易控制：

- 行为确定，不容易受浮点格式影响
- 比较和边界判断更直接
- 在没有 FPU 的 MCU 上更省资源
- 测试用例更容易写清楚

所以温度使用 `temperature_c_x10`：

- `253` 表示 `25.3°C`
- `-50` 表示 `-5.0°C`

湿度使用 `humidity_rh_x10`：

- `604` 表示 `60.4%RH`
- `1000` 表示 `100.0%RH`

## 当前范围边界
当前定义的合法范围是工程上的初始约束，不是最终产品指标：

- 温度：`-40.0°C` 到 `85.0°C`
- 湿度：`0.0%RH` 到 `100.0%RH`
- 光照：`0` 到 `100000 lux`
- 烟雾：`0` 到 `10000 ppm`

后续如果确定真实传感器型号，可以再根据数据手册调整。

## 为什么要先做校验？
传感器数据可能来自真实硬件、串口输入、测试桩或模拟程序。越早定义合法范围，后续状态机越不容易被异常输入打坏。

当前测试覆盖了：

- 正常样本
- 最小边界
- 最大边界
- 温度越界
- 湿度越界
- 光照越界
- 烟雾越界
- 空指针输入

这些测试是后续告警状态机的地基。只有先确认输入模型可靠，告警逻辑的测试才有意义。
