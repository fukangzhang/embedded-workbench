# 传感器采集步骤

## 这一步做了什么？

项目新增了一个 app 层模块：

```text
sensor_acquisition
```

它把两件事接起来：

```text
sensor_source_read
  -> submit sample
```

换句话说，它负责“采集一帧，并把这一帧交给后面的数据流”。

## 对应代码

- `app/include/embedded_workbench/sensor_acquisition.h`
- `app/src/sensor_acquisition.c`
- `tests/test_sensor_acquisition.c`
- `app/src/rtos_port_freertos.c`

## 为什么不是直接写在 FreeRTOS task 里？

如果直接在 `sensor_acquire_task` 里写完整逻辑：

```text
读 source
校验 sample
发 queue
```

那么后续一旦要换真实传感器、增加失败统计、做主机测试，就会越来越难拆。

现在拆成：

```text
source 负责读数据
sensor_acquisition 负责把读到的数据提交出去
FreeRTOS task 负责周期调度
```

每一层只做一件事，测试也更容易。

## 接口怎么读？

头文件里有一个回调类型：

```c
typedef bool (*sensor_acquisition_submit_fn)(void *context, const sensor_sample_t *sample);
```

这表示“把一帧 sample 提交给下一站”的函数。

在 FreeRTOS 里，下一站是 queue：

```text
xQueueSend(sensor_sample_queue, sample)
```

在测试里，下一站是 fake submit context：它只记录收到几帧、最后一帧是什么。

## sensor_acquisition_poll 做了什么？

核心流程很短：

```text
1. 检查 acquisition/source/submit 是否存在
2. 调用 sensor_source_read 读取一帧 sample
3. 读取失败就返回 false
4. 读取成功后调用 submit
5. submit 成功才返回 true
```

注意：sample 的范围校验仍然由 `sensor_source_read` 统一完成。这样非法温度、湿度、光照、烟雾值不会进入后续队列。

## 它和 sequence_sensor_source 的关系

`sequence_sensor_source` 是一个数据来源。

`sensor_acquisition` 是一个搬运步骤。

它们组合起来像这样：

```text
sequence_sensor_source
  -> sensor_source_read
  -> sensor_acquisition_poll
  -> submit callback
```

后续真实传感器接入时，只需要把 sequence source 换成真实 source，`sensor_acquisition` 仍然可以继续用。

## FreeRTOS 里怎么接上？

`sensor_acquire_task` 启动时会尝试初始化：

```text
sensor_acquisition_t acquisition
source = context->sensor_source
submit = freertos_submit_sensor_sample
submit_context = context
```

之后每个周期调用 `sensor_acquisition_poll`。

如果没有配置 source，它不会产生 sample，但任务骨架仍然存在。这对早期固件构建很重要，因为我们可以先验证任务和队列能编译链接，再逐步接真实采集。

## 测试覆盖了什么？

`tests/test_sensor_acquisition.c` 覆盖：

- 成功读取两帧 sample 并提交。
- 序列读完后不再提交。
- submit 失败时返回失败。
- source 读到非法 sample 时不提交。
- 空 acquisition、空 source、空 submit 这些防御性路径。

这些测试说明采集步骤的边界已经固定下来，后续改 FreeRTOS task 或真实传感器 source 时，不容易把基础行为改坏。
