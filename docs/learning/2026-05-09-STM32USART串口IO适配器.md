# STM32 USART 串口 IO 适配器

## 这一步做了什么？

这一步新增 `stm32_usart_serial_io`，把底层 USART 单字节读写函数包装成更接近“串口服务”需要的接口。

可以这样理解：

```text
stm32_usart
  只知道 USART 寄存器和单字节读写

stm32_usart_serial_io
  把单字节读写包装成 read/write callback

serial_command_service
  负责命令行、解析、处理和响应
```

## 为什么需要这一层？

`serial_command_service` 不应该直接知道 STM32 的 `SR/DR` 寄存器。它只需要一个“能写出响应字符串”的函数。

如果让 `serial_command_service` 直接调用 `stm32_usart_write_byte`，应用层就会依赖具体芯片寄存器，后面想换成主机模拟、USB CDC、别的 UART 都会困难。

所以这个适配器的价值是：

- 上层仍然面对通用 callback。
- 底层仍然面对 USART 寄存器。
- 中间只做很薄的转换。

## 代码怎么读？

建议按这个顺序：

1. `drivers/include/embedded_workbench/stm32_usart_serial_io.h`
   - 看 `stm32_usart_serial_io_context_t`。
   - 注意 `stm32_usart_serial_io_write` 的签名和 `serial_command_service_write_fn` 一致。

2. `drivers/src/stm32_usart_serial_io.c`
   - 看 `read_byte` 如何把 `void *context` 转回真实 context。
   - 看 `write` 如何逐字节等待 TXE 并调用 `stm32_usart_write_byte`。

3. `tests/test_stm32_usart_serial_io.c`
   - 看 RXNE 没有置位时为什么读返回 false。
   - 看 TXE 没有置位时为什么写返回 false。
   - 看 TXE 置位后写 `"OK"` 为什么最后 `DR` 中是 `'K'`。

## 关键嵌入式知识点

USART 的 TXE bit 表示发送数据寄存器可以接收下一个字节。真实硬件里，一个字节写进 `DR` 后，TXE 可能会暂时清零，等硬件移走数据后再置位。

所以写一串响应时不能只假设“永远可写”。本模块用了 `max_poll_attempts` 做有限等待：

- TXE 及时变 ready：继续写。
- 一直不 ready：返回 false。

这不是最高性能方案，但适合作为早期 bring-up 的轮询串口路径。

## 和真实串口命令链路的关系

后续真实链路会长这样：

```text
USART2 RXNE
  -> stm32_usart_serial_io_read_byte
  -> serial_command_service_feed
  -> response text
  -> stm32_usart_serial_io_write
  -> USART2 TXE/DR
```

这一阶段只完成中间 I/O 适配，还没有在固件 `main` 中跑循环，也没有启用真实板卡串口收发。

## 面试时怎么讲？

可以说：

> 我给 STM32 USART 增加了一层串口 I/O 适配器，让应用层的串口命令服务只依赖 callback，而不是直接依赖寄存器。底层仍然通过 RXNE/TXE 和 DR 做轮询读写，这样后续既能接真实 USART2，也能保留主机测试和替换能力。
