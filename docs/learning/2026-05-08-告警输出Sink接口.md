# 告警输出 Sink 接口

## 这一阶段在做什么？
前面已经有两层：

```text
alarm_state -> alarm_output_command_t
```

这一阶段增加第三层：

```text
alarm_output_command_t -> alarm_output_sink
```

`alarm_output` 只回答“应该输出什么”，`alarm_output_sink` 负责把这个命令交给某个输出目标。这个输出目标现在可以是测试里的 fake，后续可以换成 STM32 GPIO、蜂鸣器或继电器驱动。

## 对应代码
- `app/include/embedded_workbench/alarm_output_sink.h`
- `app/src/alarm_output_sink.c`
- `tests/test_alarm_output_sink.c`
- `app/include/embedded_workbench/rtos_port_freertos.h`
- `app/src/rtos_port_freertos.c`

## 为什么不直接在状态机里控制 GPIO？
如果把 GPIO 控制写进状态机，会让状态判断、输出策略、硬件寄存器操作混在一起。这样有几个问题：

- 主机上很难测试
- 换开发板时要改业务逻辑
- FreeRTOS 任务里很难替换 fake 输出
- 面试时不好解释模块边界

现在的分层更清楚：

```text
alarm_state
  -> 判断现在是 normal/warning/alarm/fault

alarm_output
  -> 把状态变成 indicator/buzzer/actuator/period

alarm_output_sink
  -> 把输出命令交给具体硬件或测试 fake
```

## Sink 是什么？
这里的 `sink` 可以理解成“输出落点”。它不是硬件本身，而是一个小接口：

- `set_indicator`
- `set_buzzer`
- `set_actuator`

每个函数都是回调。测试里用 fake 回调记录有没有被调用；以后板上代码可以用真正的 GPIO 回调。

## 和 FreeRTOS 的关系
`rtos_port_freertos` 的告警输出任务现在收到告警事件后会做这几步：

```text
alarm_event.state
  -> alarm_output_command_for_state
  -> alarm_output_sink_apply
```

如果 context 里没有设置 sink，任务不会做真实输出。这让当前 FreeRTOS 骨架仍然可以构建，同时给后续硬件接入留出位置。

## 面试里怎么讲？
可以这样说：

> 我把告警控制拆成三层：状态机负责判断状态，输出策略负责把状态映射成控制命令，sink 接口负责把命令交给实际输出目标。这样核心逻辑可以在 PC 上测试，FreeRTOS 任务也只依赖抽象接口，后续接 GPIO 时不会影响状态机和阈值逻辑。
