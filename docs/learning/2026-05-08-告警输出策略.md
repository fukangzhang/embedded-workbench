# 告警输出策略

## 这一阶段在做什么？
前面已经能判断系统处于：

- normal
- warning
- alarm
- sensor_fault

但“状态”本身还不是硬件动作。硬件动作可能是：

- LED 熄灭
- LED 慢闪
- LED 快闪
- 蜂鸣器响
- 执行器打开

这一阶段新增 `alarm_output` 模块，把 `alarm_state_t` 映射成输出命令。

## 为什么这是 app 模块？
`alarm_output` 依赖 `alarm_state_t`，而 `alarm_state_t` 属于应用逻辑。

按当前架构规则：

```text
bsp -> drivers -> app
```

`drivers` 不应该依赖 `app`。所以这个“策略映射”放在 `app/`，而不是放进 `drivers/`。

后续真正控制 GPIO、PWM、蜂鸣器或继电器的代码，才会放到底层驱动或 BSP 适配里。

## 当前输出命令是什么？
当前定义：

```c
typedef struct {
    alarm_output_indicator_t indicator;
    bool buzzer_enabled;
    bool actuator_enabled;
    uint16_t period_ms;
} alarm_output_command_t;
```

它不是直接操作硬件，而是描述“应该怎么输出”。

例如：

- normal：灯灭、蜂鸣器关、执行器关
- warning：慢闪，不响蜂鸣器
- alarm：快闪，蜂鸣器开，执行器开
- sensor_fault：故障闪烁，蜂鸣器开，执行器不开

## 为什么先做纯逻辑？
纯逻辑可以在主机上测试，不需要开发板。

这一步的测试覆盖：

- normal 输出
- warning 输出
- alarm 输出
- sensor_fault 输出
- 空指针错误路径
- 未知状态错误路径
- indicator 名称转换

这样后续接真实硬件时，如果 LED 行为不对，可以更快判断问题在策略层还是硬件驱动层。

## 后续怎么接到 FreeRTOS？
后续 `alarm_output_task` 可以：

1. 从 `alarm_event_queue` 接收告警事件
2. 调用 `alarm_output_command_for_state`
3. 把输出命令交给硬件输出接口

当前阶段只完成第 2 步的纯逻辑能力。
