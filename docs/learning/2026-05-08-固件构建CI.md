# 固件构建 CI

## 这一阶段在做什么？
上一阶段已经能在本地生成 `embedded_firmware.elf`。这一阶段把这件事放进 GitHub Actions。

CI 现在有两个 job：

- `Host CMake tests`：编译并运行主机侧测试
- `Firmware ELF build`：交叉编译生成固件 ELF

这样 PR 不仅能证明业务逻辑测试通过，也能证明固件工程骨架还能链接。

## 为什么 CI 里先用 Zig？
真正面向 STM32 的常见工具链是 ARM GNU Toolchain，也就是 `arm-none-eabi-gcc`。

但当前项目还在骨架阶段，CI 里先用 PyPI 的 `ziglang` 包有几个好处：

- 安装简单
- 不需要手动缓存大工具链
- 可以验证 freestanding ARM 编译和链接
- 和本机当前验证方式一致

这不是最终工具链选择。后续硬件阶段仍然建议安装并验证真实 ARM GNU Toolchain。

## CI 里做了哪些事？
`Firmware ELF build` job 会：

1. 安装 `ninja-build`
2. 安装 `ziglang`
3. 找到 `zig` 可执行文件
4. 创建 `zig ar` 和 `zig ranlib` wrapper
5. 使用 `cmake/toolchains/zig-arm-none-eabi.cmake` 配置固件构建
6. 构建 `embedded_firmware.elf`

## 为什么不上传 ELF？
当前 ELF 只是骨架验证产物，还不能直接作为正式固件发布。

后续等加入 HAL/LL、启动配置、外设初始化和真实开发板验证后，再考虑上传 `.elf`、`.bin` 或 `.hex` artifact。

## 后续可以增强什么？
后续可以继续加：

- ARM GNU Toolchain CI job
- 固件大小检查
- `.bin`/`.hex` 生成
- artifact 上传
- OpenOCD 烧录脚本检查
- 硬件在环测试

当前阶段只要求 CI 能证明固件骨架可以被交叉编译和链接。
