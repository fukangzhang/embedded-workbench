# 告警输出节拍逻辑

## 这一阶段在做什么？
前面 `alarm_output_command_t` 里已经有 `period_ms`：

```c
typedef struct {
    alarm_output_indicator_t indicator;
    bool buzzer_enabled;
    bool actuator_enabled;
    uint16_t period_ms;
} alarm_output_command_t;
```

这一阶段把它变成可测试的节拍逻辑：

```text
command + elapsed_ms -> indicator 当前是否点亮
```

## 对应代码
- `app/include/embedded_workbench/alarm_output_timing.h`
- `app/src/alarm_output_timing.c`
- `tests/test_alarm_output_timing.c`
- `app/include/embedded_workbench/alarm_output.h`

## 当前节拍规则
当前约定：`period_ms` 表示完整闪烁周期。

一个周期内：

- 前半段：indicator 亮
- 后半段：indicator 灭

例如 `period_ms = 1000`：

```text
0ms   - 499ms  -> on
500ms - 999ms  -> off
1000ms         -> 下一轮 on
```

例如 `period_ms = 250`：

```text
0ms   - 124ms  -> on
125ms - 249ms  -> off
250ms          -> 下一轮 on
```

## 为什么先做纯逻辑？
输出节拍最终可能由 FreeRTOS task、timer 或硬件定时器驱动。但节拍规则本身不依赖这些东西。

先做纯逻辑有几个好处：

- 可以在主机上快速测试边界
- 后续接 FreeRTOS 时不用重新讨论“什么时候亮、什么时候灭”
- 面试时可以说明自己把调度机制和业务规则分开了

## 和后续 FreeRTOS 的关系
后续任务可以周期性调用：

```text
alarm_output_indicator_is_on(command, elapsed_ms, &is_on)
```

然后把 `is_on` 转成 `digital_output_write` 的高/低电平。这样 FreeRTOS 只负责“什么时候调用”，节拍模块负责“应该亮还是灭”。

## 面试里怎么讲？
可以这样说：

> 我把指示灯闪烁节拍做成了纯函数：输入输出命令和经过时间，输出当前应该亮还是灭。这样不用依赖 FreeRTOS 或硬件定时器也能测试节拍规则，后续只需要由任务调度周期性调用即可。
