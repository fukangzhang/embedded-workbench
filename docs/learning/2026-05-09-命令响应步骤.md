# 命令响应步骤

## 这一步做了什么？

项目新增了一个 app 层模块：

```text
command_responder
```

它负责处理已经解析好的 `command_t`，并生成完整响应文本：

```text
command_t
  -> command_handler
  -> response_format
  -> response text
```

## 对应代码

- `app/include/embedded_workbench/command_responder.h`
- `app/src/command_responder.c`
- `tests/test_command_responder.c`
- `app/src/rtos_port_freertos.c`
- `app/include/embedded_workbench/rtos_port.h`
- `app/src/rtos_task_model.c`

## 为什么不是继续在 communication_task 里回固定 OK？

固定 `OK` 只能说明：

```text
command_queue -> communication_task -> response_queue
```

这条队列通了。

但它不能说明命令真的被处理了。现在 `communication_task` 收到 `command_t` 后，会走：

```text
command_responder_handle_command
  -> command_handler_handle
  -> response_format_result/config/status
```

所以 `STATUS`、`CONFIG`、`SET`、`SAMPLE`、`CLEAR_ALARM` 这些命令在 FreeRTOS 通信任务里也有了真实处理路径。

## command_responder 保存了什么？

```c
typedef struct {
    alarm_config_t *config;
    alarm_state_t *state;
    sensor_sample_t *sample;
} command_responder_t;
```

它保存的是指针，不复制状态。原因是 `SET` 和 `SAMPLE` 命令需要把结果写回调用者持有的状态。

例如：

- `SET TEMP_WARN 360` 会修改 `config`
- `SAMPLE 360 600 250 20` 会修改 `sample`
- 配置或样本改变后会重新计算 `state`

## 它和 command_session 有什么区别？

`command_session` 的入口是文本行：

```text
"STATUS?\n"
```

它内部会先调用 parser。

`command_responder` 的入口是已经解析好的结构体：

```text
command_t
```

所以它更适合 FreeRTOS 通信任务，因为通信任务的 `command_queue` 里放的就是 `command_t`。

## 为什么 response message 改成 512 字节？

以前 `rtos_response_message_t` 只有 128 字节，因为通信任务只返回固定 `OK`。

但真实响应可能包含：

```text
OK result=ok
CONFIG ...
STATUS ...
```

这些内容明显超过 128 字节。现在项目显式定义：

```c
#define RTOS_RESPONSE_MESSAGE_TEXT_SIZE 512u
```

`rtos_task_model` 也用 `sizeof(rtos_response_message_t)` 创建 `response_queue`，确保队列复制大小和真实消息结构一致。

## FreeRTOS 里怎么接上？

`communication_task` 启动时创建：

```text
command_responder_t responder
config = alarm_config_default()
state = ALARM_STATE_NORMAL
sample = default sample
```

之后任务阻塞等待 `command_queue`：

```text
xQueueReceive(command_queue)
  -> command_responder_handle_command
  -> xQueueSend(response_queue)
```

这样通信任务不再只是队列骨架，而是开始复用现有命令处理和响应格式化逻辑。

## 当前还缺什么？

当前通信任务和环境处理任务各自持有一份 config/state/sample。也就是说，`SET` 命令能影响通信任务自己的响应状态，但还没有同步给环境处理任务。

后续要让 FreeRTOS 运行闭环更完整，需要设计一条配置同步路径，例如配置命令事件、共享配置快照或专门的 config queue。
