# 传感器样本滤波

## 这一步做了什么？

新增模块：

```text
drivers/include/embedded_workbench/sensor_sample_filter.h
drivers/src/sensor_sample_filter.c
```

它对 `sensor_sample_t` 做一阶平滑，让样本不会完全跟着每次原始采样跳动。

## 为什么嵌入式里常需要滤波？

真实传感器会有抖动：

- ADC 读数会跳。
- 温湿度传感器可能有短时误差。
- 光照、烟雾这种环境量也可能突然尖峰。

如果直接拿原始值做阈值判断，系统可能在 warning/normal 之间来回切。滤波能让输入更稳定。

## 为什么不用 float？

这个模块使用整数权重：

```text
alpha_numerator / alpha_denominator
```

例如：

```text
1 / 4
```

表示“新样本占四分之一，历史样本占四分之三”。

这样写的好处是：

- 主机测试和 MCU 固件结果一致。
- 不依赖 FPU。
- 边界行为容易用整数测试固定下来。

固件真正引用滤波器后，还要注意一点：不能随手使用 64 位除法。当前实现把 `delta * alpha` 拆成“整数部分 + 余数部分”，保持 32 位运算，避免在 freestanding ARM 链接时额外依赖编译器运行时除法函数。

## 公式怎么理解？

核心公式是：

```text
filtered = previous + (input - previous) * alpha
```

如果上一帧温度是 `20.0 C`，新输入是 `40.0 C`，`alpha=1/2`，输出就是：

```text
30.0 C
```

如果 `alpha=1/4`，输出就是：

```text
25.0 C
```

`alpha` 越小，输出越稳，但响应越慢。`alpha` 越大，输出越快跟随输入，但抖动也更多。

## 当前还没有接入运行链路

这一步只是提供独立模块和测试。

也就是说，当前 `host_sim`、FreeRTOS 任务和告警状态机行为还没有改变。

后续接入时，比较自然的位置有两个：

- `sensor_acquisition` 读到样本后先滤波，再提交。
- `env_process_task` 从队列取出样本后先滤波，再做阈值判断。
- 用 `filtered_sensor_source` 先包住原始 source，再把包好的 source 交给采集链路。

这些位置含义不同，后续应该单独写计划决定。当前已经新增了 `filtered_sensor_source` 作为组合层，但默认运行链路还没有启用它。

## 看完要能解释什么？

- 为什么真实传感器输入常常需要滤波
- 为什么这里用整数而不是浮点
- 为什么 MCU freestanding 固件里要避免不必要的 64 位除法
- `alpha` 越大或越小分别意味着什么
- 为什么这一步还不改变现有告警行为
- `filtered_sensor_source` 为什么只是组合入口，不等于滤波已经默认启用
