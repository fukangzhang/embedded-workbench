# 数字输出驱动抽象

## 这一阶段在做什么？
前面已经有板级 profile：

```text
board_profile -> alarm_led / alarm_buzzer / alarm_actuator
```

这一阶段增加一个通用数字输出驱动抽象：

```text
board_pin_t -> digital_output_write
```

它只负责表达“把某个板级引脚写成高电平或低电平”，不关心这个引脚是告警灯、蜂鸣器还是执行器。

## 对应代码
- `drivers/include/embedded_workbench/digital_output.h`
- `drivers/src/digital_output.c`
- `tests/test_digital_output.c`
- `bsp/include/embedded_workbench/board_profile.h`

## 为什么放在 drivers？
`digital_output` 是一个可复用驱动抽象。它使用 BSP 提供的 `board_pin_t`，但不依赖应用层。

这样依赖方向保持为：

```text
bsp -> drivers -> app
```

也就是说：

- `bsp` 负责说明板子上有哪些引脚
- `drivers` 负责把“写一个输出脚”变成统一接口
- `app` 后续可以把告警输出策略交给驱动，但驱动本身不知道告警状态机

## 现在为什么还是 fake？
当前 `digital_output_controller_t` 里面只有一个 `write` 回调。测试里用 fake 回调记录调用参数：

- 写了哪个 `board_pin_t`
- 写成了 `high` 还是 `low`
- 底层失败时是否能把失败结果传回来

这一步还没有写 STM32 GPIO 寄存器，也没有调用 HAL。这样做是为了先固定接口和测试，后续真实硬件接入时替换回调即可。

## 和告警输出的关系
现在链路已经越来越完整：

```text
alarm_state
  -> alarm_output_command_t
  -> alarm_output_sink
  -> digital_output
  -> board_pin_t
```

本次只完成 `digital_output` 这一层。下一步可以写一个适配器，把 `alarm_output_sink` 的 `set_indicator/set_buzzer/set_actuator` 映射到三个 `digital_output_write` 调用。

## 面试里怎么讲？
可以这样说：

> 我没有让告警状态机直接操作 GPIO，而是先建立了 board profile、输出策略、sink 和 digital output 几层边界。digital output 只知道板级引脚和高低电平，所以可以在 PC 上用 fake 测试，后续再替换成 STM32 HAL 或寄存器实现。
