# 项目路线与前后端取舍

## 先回答：这个项目需要前后端都有吗？
短期不需要完整前后端。这个项目的核心是嵌入式软件能力，最重要的是把 `C` 代码、模块边界、测试、协议、状态机和后续 `FreeRTOS` 接入做扎实。

为了学习和简历展示，推荐路线是：

1. 第一优先级：嵌入式核心逻辑
   - 传感器数据模型
   - 阈值判断与告警状态机
   - 参数配置
   - 串口协议解析
   - 主机侧自动化测试

2. 第二优先级：主机仿真入口
   - 用命令行程序模拟设备运行
   - 打印传感器数据、告警状态、配置变化
   - 让没有开发板时也能演示项目

3. 第三优先级：可选可视化界面
   - 后期可以做一个简单上位机或 Web Dashboard
   - 它用于展示数据和配置阈值，不作为项目核心
   - 如果时间有限，先用 CLI 和测试报告展示即可

所以这里的“前端/后端”不能按普通 Web 项目理解。更准确的分层是：

- 嵌入式端：`C + FreeRTOS + drivers + app`
- 主机仿真端：`C` 测试程序或 CLI
- 可选展示端：后期再考虑 Web UI、串口上位机或数据面板

## 为什么先主机仿真？
真实硬件开发会被很多外部因素拖住，例如开发板型号、引脚、驱动库、下载器、串口工具、传感器模块是否到位。主机仿真优先可以先把最有含金量的逻辑做出来：

- 状态机是否正确
- 阈值边界是否正确
- 命令解析是否健壮
- 模块接口是否清晰
- 测试是否能证明行为

等这些稳定后，再把底层数据来源替换成真实 `STM32` 外设。

## 推荐阶段计划

### 第一阶段：项目定义与规则
目标是让项目知道自己要做什么，以及以后如何推进。

产出：
- 中文 README
- 架构说明
- 工作流程
- 产品说明
- 学习笔记入口

### 第二阶段：主机 C 工程骨架
目标是让项目真正能编译和运行最小 C 程序。

产出：
- `app/`、`drivers/`、`tests/` 的最小源码
- CMake 构建目标
- 一个可以在主机运行的测试程序

### 第三阶段：传感器抽象与数据模型
目标是定义“传感器数据如何进入系统”。

产出：
- 温湿度、光照、烟雾等数据结构
- 模拟传感器输入
- 基础边界测试

### 第四阶段：告警状态机
目标是完成项目最核心的业务逻辑。

产出：
- 正常、预警、告警、恢复等状态
- 阈值判断
- 恢复条件
- 单元测试覆盖主要边界

### 第五阶段：通信命令解析
目标是让外部可以查看状态和修改配置。

产出：
- 串口风格命令格式
- 查询状态命令
- 设置阈值命令
- 错误输入处理

### 第六阶段：FreeRTOS 任务骨架
目标是把主机验证过的逻辑组织成任务模型。

产出：
- 采集任务
- 处理任务
- 通信任务
- 告警任务
- 队列或消息接口设计

### 第七阶段：STM32 目标板接入
目标是把可验证逻辑迁移到真实硬件。

产出：
- BSP 初始化
- UART/I2C/SPI 驱动适配
- 真实传感器或模拟外设接入
- 板上演示说明

## 面试表达方向
这个项目后期可以这样讲：

> 我做了一个基于 STM32/FreeRTOS 思路的环境监测与告警控制终端。前期采用主机仿真优先，把传感器抽象、告警状态机和串口命令解析独立成可测试模块，之后再通过 BSP 和 driver 接口替换为真实硬件实现。这样既能保证业务逻辑可验证，也能降低硬件调试对项目进度的影响。
