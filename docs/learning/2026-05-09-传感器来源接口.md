# 传感器来源接口

## 这一步做了什么？

项目新增了一个接口：

```text
sensor_source
```

它用于表示“系统从哪里读取一帧传感器样本”。这个来源可以是：

- 测试 fake
- 主机模拟序列
- 后续真实 I2C/SPI/ADC 传感器驱动

## 为什么需要 source 接口？

前面已经有：

```text
sensor_sample_t
```

它只是“一帧数据”的结构，不负责说明这帧数据从哪里来。

如果后续把真实传感器读取代码直接写进状态机，状态机会同时承担两件事：

- 读取硬件
- 判断告警

这会让模块很难测试。现在拆成：

```text
sensor_source -> sensor_sample -> alarm_state
```

状态机继续只关心 sample，source 负责把 sample 读出来。

## 接口长什么样？

```c
typedef bool (*sensor_source_read_fn)(void *context, sensor_sample_t *sample_out);

typedef struct {
    sensor_source_read_fn read;
    void *context;
} sensor_source_t;
```

`read` 是函数指针，意思是“调用这个函数读取一帧 sample”。

`context` 是具体实现自己的状态。比如测试 fake 可以把预设 sample 放在 context 里；真实 I2C 传感器可以把 I2C 地址、寄存器缓存、错误计数放在 context 里。

## 为什么还要 sensor_source_read 包装一层？

如果每个调用者都直接调用 `source->read(...)`，就容易漏掉校验。

所以项目提供：

```c
bool sensor_source_read(const sensor_source_t *source, sensor_sample_t *sample_out);
```

它会统一检查：

1. source 是否为空。
2. read callback 是否为空。
3. 输出指针是否为空。
4. callback 是否读取成功。
5. 读出的 sample 是否通过 `sensor_sample_is_valid`。

## FreeRTOS 采集任务现在怎么用？

`freertos_rtos_port_context_t` 新增：

```c
sensor_source_t *sensor_source;
```

`sensor_acquire_task` 每个周期会通过 `sensor_acquisition_poll` 尝试：

```text
sensor_source_read
  -> sensor_acquisition submit callback
  -> xQueueSend(sensor_sample_queue)
```

如果没有配置 source，任务保持原来的周期骨架，不产生 sample。这样早期固件仍然能构建，后续接真实传感器时再把 source 填进去。

## 和 SAMPLE 命令有什么区别？

`SAMPLE` 是手工注入，用于串口调试和演示。

`sensor_source` 是采集入口，用于后续模拟或真实传感器读取。

当前已经有一个模拟实现：`sequence_sensor_source`。它按照预设数组顺序输出 sample，`host_sim` 的 demo 路径已经通过它读取样本。

后续还可以把 source 包一层 `filtered_sensor_source`：

```text
sequence_sensor_source / real_sensor_source
  -> filtered_sensor_source
  -> sensor_acquisition
```

这样上层仍然只看到 `sensor_source_t`，但读到的是滤波后的 sample。

两者最后都会变成 `sensor_sample_t`，但来源不同：

```text
SAMPLE command -> 手工输入 sample
sensor_source -> 周期采集 sample
```

## 这一步还没完成什么？

它还没有接真实传感器，也没有证明 FreeRTOS 调度器已经在板上跑起来。

它只是把“读取 sample 的接口”和“采集任务怎么把 sample 发进队列”先固定下来。`filtered_sensor_source` 已经提供可选组合层，但还没有默认装配进运行链路。
