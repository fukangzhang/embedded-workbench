# 主机仿真告警输出状态展示

## 这一阶段在做什么？
前面已经有了告警输出策略：

```text
alarm_state -> alarm_output
```

这一阶段把它接到可运行的主机仿真和状态响应里。这样运行 `host_sim` 时，不只看到当前状态是 `normal`、`warning` 或 `alarm`，还能看到这个状态会要求哪些输出动作。

## 对应代码
- `app/src/alarm_output.c`
- `app/src/response_format.c`
- `tools/host_sim/main.c`
- `tests/test_response_format.c`

## 为什么要这样做？
单独有 `alarm_output` 模块时，它只是一个可测试的纯逻辑模块。把它接到主机仿真后，学习路径会更顺：

```text
sensor_sample
  -> sequence_sensor_source
  -> alarm_state_update
  -> alarm_output_command_for_state
  -> host_sim / STATUS response
```

这条线对应真实嵌入式系统里的思路：

- 传感器输入决定告警状态
- 告警状态决定蜂鸣器、指示灯、执行器怎么动作
- 真实硬件还没接入前，先用主机输出把决策结果展示出来

## 现在能看到什么？
运行：

```powershell
build\host_sim.exe
```

可以看到类似输出：

```text
state=warning
output indicator=slow_blink buzzer=off actuator=off period_ms=1000
```

其中：

- `indicator` 表示指示灯模式
- `buzzer` 表示蜂鸣器是否启用
- `actuator` 表示执行器是否启用
- `period_ms` 表示闪烁或输出节奏

## 面试里怎么讲？
可以这样解释：

> 我没有一开始就把 GPIO 控制写死在告警状态机里，而是先把状态机和输出策略分开。状态机只判断当前安全状态，输出策略再把状态映射成指示灯、蜂鸣器和执行器命令。这样主机侧可以先测试和演示核心逻辑，后续接 STM32 GPIO 或 FreeRTOS 任务时也不用重写状态机。
