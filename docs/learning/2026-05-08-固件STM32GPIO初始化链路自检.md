# 固件 STM32 GPIO 初始化链路自检

## 这一阶段在做什么？
前面已经有了目标板 GPIO 初始化的三段逻辑：

```text
stm32_rcc_gpio_clock
  -> stm32_gpio_config
  -> stm32_board_gpio_init
```

这一阶段把它接进 `firmware/src/main.c` 的固件自检入口。也就是说，固件构建目标现在不仅能链接这些模块，还会在 `main` 里实际调用一次初始化链路。

## 对应代码
- `firmware/src/main.c`
- `drivers/include/embedded_workbench/stm32_board_gpio_init.h`
- `drivers/src/stm32_board_gpio_init.c`

## 自检做了什么？
`firmware_stm32_gpio_init_self_check` 使用静态变量模拟寄存器：

```text
firmware_rcc_ahb1enr
firmware_gpioa_registers
firmware_gpiob_registers
```

然后按这个流程执行：

```text
绑定 "PA" / "PB" 到 RCC enable bit
绑定 "PA" / "PB" 到 GPIO 配置寄存器块
调用 stm32_board_gpio_init_alarm_outputs
检查 PA/PB 时钟 bit 已打开
检查 PA5、PB6、PB7 都被配置为 output
```

## 为什么仍然用模拟寄存器？
当前项目还没有接真实 STM32 CMSIS/HAL 头文件，也还没有把 RCC/GPIO 地址绑定到真实硬件地址。

所以这一阶段的价值是：

- 确认固件目标能链接这些 STM32 初始化模块
- 确认 `main` 能按预期调用初始化链路
- 确认初始化结果能被固件自检观察到

它不是板上点灯验证。

## 和前面自检的关系
现在 `firmware_self_check` 需要同时满足几类检查：

- board profile 合法
- RTOS task model 合法
- 命令处理和响应格式正常
- 告警输出链路能把 alarm 映射到三个输出
- STM32 GPIO 初始化链路能完成 RCC + GPIO config
- FreeRTOS 构建模式下队列自检正常

这让固件入口越来越像一个“早期 bring-up 自检清单”。

## 这一步还不能证明什么？
它还不能证明：

- 真实 RCC 地址正确
- 真实 GPIOA/GPIOB 地址正确
- NUCLEO-F401RE 板上的 PA5 LED 真的亮
- 蜂鸣器/执行器外设已经连接

这些需要后续真实地址绑定和板上运行验证。

## 面试里怎么讲？
可以这样说：

> 我在 firmware main 中加入了 GPIO 初始化链路自检，用模拟寄存器验证固件目标能串起 RCC 时钟、GPIO 输出配置和 board_profile 中的告警输出引脚。这样在接真实寄存器地址前，先保证模块链接、调用顺序和基本位操作都能在固件构建目标里通过。
