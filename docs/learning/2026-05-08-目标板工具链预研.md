# 目标板工具链预研

## 为什么要区分主机构建和目标板构建？
主机构建用于在电脑上运行：

- `host_sim`
- 单元测试
- CTest

目标板构建面向 STM32，不应该构建这些主机可执行文件。它更关心：

- BSP 静态库
- drivers 静态库
- app 静态库
- 后续启动文件、链接脚本和固件 `.elf`

所以这一阶段给 CMake 增加了两个开关：

```cmake
EW_BUILD_HOST_TOOLS
EW_BUILD_TESTS
```

默认都打开，保证本地开发体验不变。交叉编译时可以关闭它们。

## 当前新增的 toolchain 文件

`cmake/toolchains/arm-none-eabi.cmake`

这是未来使用 ARM GNU Toolchain 时的正式方向。它假设系统里有：

```text
arm-none-eabi-gcc
arm-none-eabi-ar
arm-none-eabi-ranlib
```

`cmake/toolchains/zig-arm-none-eabi.cmake`

这是当前本机验证用的替代方案。它使用 Zig 的 C 编译能力，面向 `thumb-freestanding-eabi` 编译静态库。

## 为什么当前只编译静态库？
生成真正固件还需要：

- 启动文件
- 链接脚本
- 中断向量表
- HAL/LL 或寄存器初始化
- `SystemInit`
- `_sbrk`、`_write` 等系统调用桩，取决于 C 库使用情况

这些还没接入，所以现在只验证核心库能否面向 ARM freestanding 编译。

## 这次预研暴露了什么问题？
目标库构建最初暴露了两个问题：

1. `command_parser.c` 依赖 `errno.h` 和 `stdlib.h`
2. `response_format.c` 依赖 `stdio.h`

这些在主机上很自然，但在 bare-metal/freestanding 环境里不一定存在。

因此本阶段顺手做了两点改进：

- 命令解析改为自实现 `int32_t` 解析和字符串比较
- 响应格式改为自实现轻量 writer，不再依赖 `snprintf`

这让核心库更接近 MCU 可移植代码。

## 当前验证命令
主机验证：

```powershell
cmake -S . -B build -G Ninja
cmake --build build
ctest --test-dir build --output-on-failure
```

目标库验证：

```powershell
cmake -S . -B build-arm -G Ninja `
  -D CMAKE_TOOLCHAIN_FILE=cmake/toolchains/zig-arm-none-eabi.cmake `
  -D EW_BUILD_HOST_TOOLS=OFF `
  -D EW_BUILD_TESTS=OFF

cmake --build build-arm
```

当前目标库验证已经通过，可以生成：

- `libembedded_bsp.a`
- `libembedded_drivers.a`
- `libembedded_app.a`
