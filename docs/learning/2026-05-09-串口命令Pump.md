# 串口命令 Pump

## 这一步做了什么？

这一步新增 `serial_command_pump`。它的作用是把“从串口读取字节”和“把字节交给命令服务”这两件事接起来。

可以这样理解：

```text
reader callback
  -> serial_command_pump_poll
  -> serial_command_service_feed
  -> writer callback
```

reader 负责提供输入字节，service 负责解析命令和生成响应，writer 负责把响应发出去。

## 为什么不直接写 while 循环？

当然可以在 `firmware/main.c` 里直接写：

```text
while (read_byte(...)) {
    serial_command_service_feed(...);
}
```

但这样后面会有几个问题：

- 主机测试很难复用同一段逻辑。
- FreeRTOS task 里又要再写一遍类似循环。
- 每轮最多处理多少字节、什么时候停下来，这些规则会散落在不同入口。

所以项目把这段循环收成一个小模块，后续真实 USART2、host fake、RTOS task 都能共用。

## 代码怎么读？

建议按这个顺序：

1. `app/include/embedded_workbench/serial_command_pump.h`
   - 看 `serial_command_pump_read_fn`。
   - 看 `serial_command_pump_poll` 的参数。

2. `app/src/serial_command_pump.c`
   - 看 reader 返回 `false` 时为什么停下来并返回 `IDLE`。
   - 看 service 返回 `RESPONSE_SENT/OVERFLOW/ERROR` 时为什么立刻停。

3. `tests/test_serial_command_pump.c`
   - 看没有数据时为什么是 `IDLE`。
   - 看半行命令为什么不会响应。
   - 看完整 `STATUS?\n` 为什么会发送响应。
   - 看 `max_bytes` 如何限制单次 poll 的工作量。
   - 看 overflow 如何原样返回给调用者。

## 关键嵌入式知识点

MCU 里主循环或 RTOS task 不应该一次做无限工作。否则一个串口输入很多字节时，其他任务可能长时间得不到运行机会。

所以 `serial_command_pump_poll` 有一个 `max_bytes` 参数。它表达的是：

- 每轮最多处理多少输入字节。
- 如果还没处理完，下一轮再继续。
- 如果已经收到完整命令，先返回，让外层有机会处理状态、调度或记录。

这是一种很常见的嵌入式“有界轮询”写法。

## 和 USART2 的关系

后续固件可以这样接：

```text
stm32_usart_serial_io_read_byte
  -> serial_command_pump_poll
  -> serial_command_service_feed
  -> stm32_usart_serial_io_write
```

当前 `firmware/src/main.c` 已经在 USART2 命令服务自检中引用了它，但仍然使用 text reader 和模拟 USART2 寄存器。真实 USART2 RX polling loop 还没有启用。

## 面试时怎么讲？

可以说：

> 我把串口命令处理拆成了 service 和 pump 两层。service 处理单个 byte 和响应，pump 负责从任意非阻塞 reader 中有界拉取字节。这样真实 USART、主机模拟和 FreeRTOS task 都可以复用同一套命令链路。
