# 固件 USART2 命令服务自检

## 这一阶段在做什么？

这一步把前面几条链路接到一起：

```text
serial_command_pump
  -> serial_command_service
  -> stm32_usart_serial_io
  -> USART2 fake registers
```

固件入口会模拟输入一条 `STATUS?\n` 命令，让 pump 从 reader callback 读取字节并喂给串口命令服务。命令服务生成响应后，再通过 USART2 I/O 适配器写到模拟 `DR` 寄存器。

## 对应代码

- `firmware/src/main.c`
- `app/include/embedded_workbench/serial_command_pump.h`
- `app/src/serial_command_pump.c`
- `app/include/embedded_workbench/serial_command_service.h`
- `app/src/serial_command_service.c`
- `drivers/include/embedded_workbench/stm32_usart_serial_io.h`
- `drivers/src/stm32_usart_serial_io.c`

## 自检做了什么？

`firmware_usart2_command_service_self_check` 做了这些事：

1. 准备 `rx_buffer`、`line_buffer`、`response_buffer`。
2. 初始化 `stm32_usart_serial_io_context_t`。
3. 初始化 `serial_command_service_t`，并把 writer 设置成 `stm32_usart_serial_io_write`。
4. 通过 `serial_command_pump_poll` 从 text reader 读取 `STATUS?\n`。
5. 检查 pump 返回 `RESPONSE_SENT`。
6. 检查响应以 `OK` 开头。
7. 检查模拟 USART2 `DR` 最后写入的是换行。

## 为什么只检查最后一个 DR 字节？

USART 的 `DR` 是发送数据寄存器，不是历史日志。连续写 `"OK ...\n"` 时，`DR` 会被每个字节覆盖，最后只能看到最后写入的字节。

所以这里的检查重点不是“保存完整响应”，而是证明：

- pump 确实把 reader 里的字节交给了命令服务。
- 命令服务确实生成了响应。
- writer callback 确实被调用。
- writer 确实走到了 USART2 I/O 适配器。

完整响应内容已经由 `serial_command_service` 的主机测试覆盖。

## 这还不是板上串口交互

这一步还不能证明：

- 电脑串口助手能收到响应。
- NUCLEO-F401RE 的 PA2/PA3 上有真实串口波形。
- 固件已经有持续运行的 RX 轮询循环。

它只是把固件里的“命令服务 -> USART writer”链路先固定下来，下一步再接真实 RX 输入。

## 面试时怎么讲？

可以说：

> 我先在固件入口里做了 USART2 命令服务自检：用模拟 reader 经过 serial_command_pump 喂给 serial_command_service，再用 STM32 USART I/O 适配器把响应写到模拟 USART2 寄存器。这样在真实串口循环前，先证明 reader、pump、命令服务和底层 USART writer 的接口已经能接起来。
