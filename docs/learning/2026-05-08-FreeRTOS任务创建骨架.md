# FreeRTOS 任务创建骨架

## 这一阶段在做什么？
上一阶段已经把 `rtos_port` 接到了 FreeRTOS queue。

这一阶段继续往前走一步：让 `rtos_port_start()` 在 FreeRTOS 构建下调用 `xTaskCreate`，创建任务模型中定义的四个任务：

- `sensor_acquire`
- `env_process`
- `communication`
- `alarm_output`

注意：这一步只创建任务，不启动调度器。

## xTaskCreate 是什么？
`xTaskCreate` 是 FreeRTOS 用来创建动态任务的 API。

它需要几个核心参数：

- 任务函数
- 任务名称
- 栈大小
- 传给任务函数的参数
- 优先级
- 保存任务句柄的指针

当前代码从 `rtos_task_model` 读取任务名称、栈大小和优先级，再调用 `xTaskCreate` 创建任务。

## TaskHandle_t 是什么？
`TaskHandle_t` 是 FreeRTOS 用来引用一个任务的句柄。

创建任务成功后，FreeRTOS 会把句柄写到我们传进去的变量里。后续如果要删除任务、查询任务状态、发通知，都可以通过这个 handle 找到对应任务。

当前 `freertos_rtos_port_context_t` 保存四个 handle：

```c
TaskHandle_t sensor_acquire_task;
TaskHandle_t env_process_task;
TaskHandle_t communication_task;
TaskHandle_t alarm_output_task;
```

这也让 `rtos_port_start()` 可以避免重复创建任务。

## 当前四个任务函数做什么？
现在还不是完整业务逻辑，只是最小骨架：

- `sensor_acquire_task`：保留周期任务形状，后续接真实采集
- `env_process_task`：从传感器队列阻塞读取样本，并更新告警状态
- `communication_task`：从命令队列阻塞读取命令，并发出一个 `OK` 响应
- `alarm_output_task`：保留周期输出任务形状，后续接 LED、蜂鸣器或执行器

这已经形成了真实 RTOS 项目常见的结构：任务通过队列协作，而不是互相直接调用。

## 为什么仍然不启动调度器？
`vTaskStartScheduler()` 一旦成功，代码就进入 FreeRTOS 调度循环，正常情况下不会返回。

如果现在直接启动它，还缺几个真实板级条件：

- SysTick 是否接入正确
- SVC/PendSV handler 是否正确
- 中断优先级是否正确
- 当前 Zig 临时工具链是否适合做运行级验证
- 真实任务栈大小是否需要板上调试

所以当前只验证“任务可以创建并链接进固件”。调度器启动会单独作为下一阶段。

## 为什么这次不用 pdMS_TO_TICKS？
项目当前配置是：

```c
configTICK_RATE_HZ = 1000
```

也就是 1 tick = 1 ms。

在当前 Zig freestanding 构建路径下，`pdMS_TO_TICKS` 会引出额外的 ARM EABI 64 位除法辅助符号。为了让这一阶段聚焦在任务骨架本身，当前直接把 `period_ms` 转成 `TickType_t` 使用。

后续换真实 ARM GNU Toolchain 或补完整运行时后，可以再恢复通用的毫秒到 tick 转换。

## 当前验证说明
本阶段验证：

- host 测试仍然通过
- 普通 firmware ELF 仍然能构建
- FreeRTOS firmware ELF clean-first 构建通过

这说明任务创建骨架已经接入，但还没有声称板上调度可运行。

## 后续还缺什么？
下一步可以专门处理调度器启动：

- 明确 `rtos_port_start()` 是否应该直接调用 `vTaskStartScheduler`
- 处理 `vTaskStartScheduler()` 不返回的问题
- 准备 SysTick/PendSV/SVC 的板级验证记录
- 开始把任务函数从“骨架”推进到真实数据流
