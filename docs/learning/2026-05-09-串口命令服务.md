# 串口命令服务

## 这一步做了什么？

本步骤新增 `serial_command_service`，它把三件事接起来：

```text
UART/终端输入的 byte
  -> serial_line_feed
  -> command_session_handle_line
  -> write callback
  -> UART/终端输出响应
```

它目前还不是 STM32 UART 驱动。它更像“串口命令业务层”：不管 byte 是从 PC 测试、host_sim、轮询 UART 还是中断 UART 来的，只要一字节一字节喂进来，服务就会在收到完整命令时生成响应。

本步骤也让 `host_sim --script` 改走这条链路，所以现有脚本化主机仿真已经在使用同一个服务。

## 为什么要单独做一层？

如果把 UART、行缓冲、命令解析、状态更新和响应发送全写在一个文件里，后面会很难测试，也很难替换真实硬件。

现在拆成这样：

- `serial_line`：只管一行怎么拼出来。
- `command_session`：只管一行命令怎么影响应用状态。
- `serial_command_service`：只管“逐字节输入”和“一段响应输出”之间的连接。
- 未来 `stm32_uart`：只管真实寄存器、收发字节、中断或轮询。

## 代码怎么读？

建议按这个顺序：

1. `app/include/embedded_workbench/serial_command_service.h`
   - 看 status enum。
   - 看 callback 类型。
   - 看为什么需要 `rx_buffer`、`line_buffer`、`response_buffer` 三块内存。

2. `app/src/serial_command_service.c`
   - 先看初始化：所有指针和 buffer 都检查一次。
   - 再看 feed：`IDLE` 表示还没收到完整命令，`RESPONSE_SENT` 表示已经发送响应。
   - 注意 overflow 只复位当前行，下一行还可以继续接收。

3. `tests/test_serial_command_service.c`
   - 看 partial input 为什么不会提前响应。
   - 看 CRLF 为什么只响应一次。
   - 看 SET 为什么能穿过完整链路更新配置和状态。
   - 看 fake writer 如何替代真实 UART 发送函数。

4. `tools/host_sim/main.c`
   - 看 `run_script_mode` 如何把 stdin 读到的字符逐字节喂给 service。
   - 看 `stdout_write` 如何模拟“把响应发出去”的动作。

## 嵌入式知识点

这里最重要的是“调用者提供内存”。在 MCU 上，串口服务通常会长期运行，不能每次收到 byte 都 malloc。所以初始化时传入固定 buffer，是更可控的做法。

另一个重点是 callback：

```c
typedef bool (*serial_command_service_write_fn)(void *context, const char *data, size_t length);
```

这表示服务不关心响应发到哪里。测试里发到内存数组；host_sim 可以发到 stdout；真实 STM32 可以发到 USART TX。这样同一个业务模块就能在不同环境复用。
