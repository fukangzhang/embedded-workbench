# FreeRTOS 配置更新队列

## 这一步做了什么？

前面 `communication_task` 已经能处理 `SET` 命令，但它修改的是通信任务自己持有的 `alarm_config_t`。

这一步新增一条内部队列：

```text
config_update_queue
```

让配置变化可以从通信任务同步到环境处理任务：

```text
SET command
  -> command_responder
  -> config_update_queue
  -> env_process_task
  -> environment_processor_update_config
```

## 为什么用队列，不直接共享变量？

FreeRTOS 里多个 task 同时读写同一个变量时，会出现并发问题。比如通信任务正在写配置，环境处理任务刚好读取配置，就可能读到半更新状态。

本项目先采用更容易解释和验证的方式：

```text
通信任务发送完整 alarm_config_t 快照
环境处理任务接收完整 alarm_config_t 快照
```

FreeRTOS queue 默认按值复制，所以 `xQueueSend` 会把配置结构体复制进队列内部，不依赖发送方局部变量的生命周期。

## command_responder 为什么要增加 status？

`command_responder` 原本只返回响应文本。通信任务只能知道“响应有没有生成成功”，不知道这条命令内部有没有修改配置。

现在新增：

```c
typedef struct {
    bool config_changed;
    bool sample_changed;
} command_responder_status_t;
```

`SET` 成功时 `config_changed = true`，通信任务就把当前配置快照发送到 `config_update_queue`。

旧入口 `command_responder_handle_command` 仍然保留，方便不关心元数据的调用方继续使用。

## env_process_task 怎么消费配置？

环境处理任务每轮先清空配置更新队列：

```text
xQueueReceive(config_update_queue, timeout=0)
  -> environment_processor_update_config
```

然后再等待传感器样本：

```text
xQueueReceive(sensor_sample_queue, timeout=env_process period)
  -> environment_processor_process_sample
```

这样即使暂时没有新 sample，配置也不会因为 `sensor_sample_queue` 的永久阻塞而一直卡住。

## 这一层的边界是什么？

这一层只负责 FreeRTOS 任务之间同步配置快照，不改变文本协议，也不直接操作硬件。

配置合法性仍由两层保护：

- `command_handler` 拒绝破坏阈值关系的 `SET`。
- `environment_processor_update_config` 只接受完整合法配置，非法快照不会覆盖旧配置。

## 看完要能解释什么？

- `config_update_queue` 为什么是 `communication -> env_process` 的单向队列
- 为什么队列里放完整 `alarm_config_t`，而不是放指针
- `command_responder_status_t` 如何把“命令副作用”告诉 FreeRTOS 通信任务
- 为什么环境处理任务不能永远阻塞在 sample queue 上
