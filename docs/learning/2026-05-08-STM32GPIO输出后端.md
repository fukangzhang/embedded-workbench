# STM32 GPIO 输出后端

## 这一阶段在做什么？
前面已经有了通用的数字输出接口：

```text
alarm_output
  -> alarm_output_digital_sink
  -> digital_output
```

这一阶段给 `digital_output` 增加一个更接近真实 STM32 的后端：`stm32_gpio_output`。它把“某个板级引脚输出高/低电平”转换成对 STM32 `GPIOx_BSRR` 寄存器的写入。

## 对应代码
- `drivers/include/embedded_workbench/stm32_gpio_output.h`
- `drivers/src/stm32_gpio_output.c`
- `tests/test_stm32_gpio_output.c`
- `CMakeLists.txt`

## BSRR 是什么？
`BSRR` 可以理解成 STM32 GPIO 的“原子置位/复位寄存器”：

- 写低 16 位：把对应 pin 置为高电平
- 写高 16 位：把对应 pin 复位为低电平

例如：

```text
PA5 high -> GPIOA_BSRR = 1 << 5
PA5 low  -> GPIOA_BSRR = 1 << (5 + 16)
```

这样不需要先读 GPIO 输出寄存器再改其中一位，适合中断和 RTOS 任务可能同时运行的场景。

## 为什么先只写 BSRR？
真实板上让一个 GPIO 工作，通常还需要：

- 打开 GPIO 端口时钟
- 配置 pin 为 output mode
- 配置 pull-up/pull-down、speed、output type

但这些更像板级初始化或 HAL/CMSIS 接入内容。当前项目还没正式接厂商 SDK，所以这一阶段先只完成“输出动作”这一小块，让后续真实硬件接入有明确落点。

## 代码怎么读？
建议按这个顺序看：

1. `stm32_gpio_output.h`
   - 看 `stm32_gpio_output_port_t`
   - 它把 `"PA"`、`"PB"` 这样的端口名绑定到一个 `BSRR` 地址
2. `stm32_gpio_output.c`
   - 看 `find_port`
   - 再看 `stm32_gpio_write`
   - 重点理解 high 写低 16 位、low 写高 16 位
3. `tests/test_stm32_gpio_output.c`
   - 看主机测试如何用普通变量模拟 `GPIOA_BSRR`
   - 这说明不插开发板也能先验证寄存器写法

## 和前面模块怎么连？
现在输出链路可以理解成两种后端：

```text
alarm_output_digital_sink
  -> digital_output
      -> board_digital_output      # 主机侧记录电平，适合测试
      -> stm32_gpio_output         # STM32 风格 BSRR 写入，接近真实硬件
```

`board_digital_output` 更像“仿真后端”，`stm32_gpio_output` 更像“目标板后端”。两者都实现同一个 `digital_output_controller_t` 操作表，所以 app 层不需要知道底下是哪一种。

## 这一步还不能证明什么？
这一步还不能证明真实板上的 LED 会亮。它只证明：

- 端口名能匹配到 GPIO 绑定
- pin 编号能转成 BSRR bit
- high/low 写法正确
- 错误端口和非法参数会失败

真实板上还需要补 GPIO 初始化和板上运行验证。

## 面试里怎么讲？
可以这样说：

> 我把数字输出接口进一步接到了 STM32 GPIO 的 BSRR 写法上。为了不依赖开发板，我先用主机单元测试模拟寄存器，验证高低电平会分别写 BSRR 的置位区和复位区。这样 app 层仍然只依赖 digital_output 抽象，后续替换为真实 GPIO 地址即可。
